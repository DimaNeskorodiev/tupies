# A useful retained knowledge unit

Use these fields where they affect understanding or later application; do not fill unsupported fields with guesses. Group related units in a readable Brain topic note.

| Field | Retain |
| --- | --- |
| Idea or method | A self-contained claim, explanation or coherent procedure. |
| Usefulness | The responsibility or decision in this bot's learning focus that it supports. |
| Applicability | Platform/version, project conditions, audience and when the idea does not apply. |
| Method details | Required inputs, steps, sequence, checks and useful worked examples. |
| Conditions and exceptions | Relevant units, thresholds, dependencies, prohibitions and failure modes. |
| Evidence | Source title/author, edition/date if known, actual page/heading/time locator and a small supporting excerpt only where needed. |
| Support type | Direct source claim, synthesis, inference, author's reported outcome or separately verified Tupies observation. |
| Integration | Related [[notes]], supporting sources, scoped alternatives, disagreement or correction. |
| Source availability | Available here, externally accessible but not rechecked, or original unavailable after processing. |

Use a meaningful title/path, useful tags and aliases. Keep the body understandable without the original; a source link alone is not learned knowledge. Store only the useful retained information and necessary bounded evidence, not a reconstruction of the whole source.

With ordinary Brain tools, these are note content conventions, not an engine-enforced knowledge schema. Do not invent active revisions, batch IDs, source hashes or verified lineage. Native study outputs can use the identities and statuses actually supplied by that flow.

After writing, read the note and check names, figures, important conditions and links. Confirm only the actual saved result. A note in a draft, a pending Skill proposal or an unverified job receipt is not an active reviewed workflow.
