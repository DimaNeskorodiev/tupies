# Apply knowledge and learn from feedback

## Use it in a task

Search Brain for the current problem, then read the relevant full notes. Select the applicable method with its prerequisites and exceptions rather than copying a generic recommendation. Retained notes can be incomplete or outdated; check changing platform facts through accessible current sources when the task needs them. If the original was discarded, say when an assertion is based on retained knowledge rather than a fresh source check.

Use actual task outcomes to distinguish a source recommendation from tested experience. Completing an audit does not establish improved traffic or ranking. A proposed experiment, successful command and measured business outcome are different evidence. Update the applicable note only after the observation is available and the current revision has been read.

## Interpret a correction

| Feedback | Appropriate update |
| --- | --- |
| Incorrect claim | Correct its supported scope and explain the evidence; preserve useful unrelated knowledge. |
| Missing condition or detail | Add the missing qualification or example to the relevant unit. |
| Wrong application | Fix method selection/applicability; do not declare the underlying rule universally false. |
| Project-specific preference | Keep it scoped to that project or the owner's preference. |
| Verified outcome | Record the conditions, observation and actual result, including failures and uncertainty. |

Use `brain_search` and `brain_read` before a correction. Preserve newer owner or synced edits through `expectedSha256` checks. A native study correction/rollback must use its actual supported controls and checked receipts; ordinary tools do not provide a multi-note atomic rollback. Denied writes, stale revisions and unavailable evidence require an honest partial result, not another route around the boundary.

## Propose a reusable Skill

Keep source-derived methods in Brain first. When the owner wants an operational workflow or repeated work establishes its usefulness, use the current reviewed Skill path. A source recommendation can be proposed before testing if it is clearly marked source-derived and untested; do not claim successful experience that did not occur.

`skills_propose` creates a pending suggestion for owner review. For a new skill, supply a distinct name, description and instructions. For an assigned mutable skill, first obtain its current SHA-256 through `skills_read` and use the offered exact revision fields. Managed catalog/import packages are immutable: propose a separately named customization rather than rewriting this learning package. `skills_create` is the exact-approved alternative for a new single-file workflow.

These tools do not create or edit resource/script files through a Skill proposal. Keep a proposed initial workflow self-contained, respect pending-proposal limits and group a coherent method instead of creating one Skill per fact. Cite actual readable source messages where supported; do not fabricate message IDs for discarded material. Use material-evidence references only if the executing Engine actually offers that schema.

A pending suggestion is not installed, assigned or authorized for execution. Read back an accepted Skill through its real assignment. Any later code resources and script runs retain separate dependency, tool and exact-execution approvals.
