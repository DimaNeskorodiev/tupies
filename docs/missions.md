# Missions

Mission is an owner goal with a durable contract, real bot episodes, saved evidence and independent acceptance. Open **Mission** in the sidebar or the five-tab phone navigation. **New Mission** chooses a coordinator, goal and Low/Medium/High/Ultra effort; optional acceptance criteria are owner-authored requirements. Medium is the default for each new Mission. Start queues the Mission once. A busy coordinator finishes its current task first.

Direct owner chat can become the same Mission. **Make this task a Mission** opens the effort picker and attaches the existing active run, snapshots and work without sending its prompt again. Ordinary chat is the default, including autonomous tool use and multi-step work. Finding a domain, comparing products, making one recommendation or report, a focused fix, several browser calls, signing in, approvals or delegation alone stay chat.

In the existing first model step, `mission_start` can return a structured `explicit` or `clear_goal` decision bound to the exact owner message. `explicit` requires an exact `explicitRequest` quote naming Mission mode. `clear_goal` requires `scope`: three to six distinct substantive requested outcomes (`quote`, `kind:deliverable|change`, `dependsOn`), connected in dependency order, plus a separate requested durable process (`process.kind:staged_execution|external_waits|recurring_work`, `process.quote`). Dependencies use zero-based earlier outcome indices; every outcome after the first must depend on an earlier one. Engine admission checks bounded fields, exact current-owner quotes and non-overlapping source spans for the outcomes and process requirement, and retains the decision in `origin.admission`. Internal search/read/compare/check steps are not independent deliverables. The model must not invent outcomes or a process need to justify promotion. Missing, conflicting or insufficient evidence leaves the same task in chat without asking the owner to select a mode; rejected first-step admission cannot be retried on a later step. No separate classification provider request is added.

After a valid inferred `clear_goal` decision, the Engine asks **Run this as a Mission?** in the same chat. Work waits for an authenticated owner choice: select an effort and **Start Mission**, or **Continue in chat**. The Engine creates no Mission before the answer; skipping/declining continues the same ordinary task and cannot trigger another proposal for that request. The card uses the existing exact question/run/generation identity, Stop and expiry lifecycle. Model output, imported content and teammate replies cannot answer it. An explicit current owner request to create a Mission starts with Medium without a redundant confirmation; an explicit level additionally needs an exact `effortQuote` from that request. Manual creation/promotion always shows the picker.

Quotes, hypothetical discussion, negation, plan-only and ambiguous requests stay ordinary chat. Semantic interpretation is still a model judgment: the Engine validates structural/source evidence, not the meaning of arbitrary prose. The explicit-name guard checks only that the quoted text names Mission mode; it cannot prove that a quoted or negated mention expresses intent. Deterministic fixtures cover adoption/refusal mechanics and labelled examples, not universal classification accuracy. The threshold intentionally favors ordinary chat when a large request lacks separate source evidence. Owner UI creation and promotion bypass automatic recognition and remain available for any task. Rooms, routines, Telegram and delegates cannot create independent Missions through this tool. If optional first-step recognition would exceed an ordinary chat’s existing context budget, that chat proceeds without a proposal. An established Mission never drops contract tools or its acceptance gate: insufficient context becomes Needs attention with a larger-context model/provider remedy. Very small context windows may fit ordinary chat and still be insufficient for the complete Mission tool catalog.

The source implementation extends A+B with shared resource admission (C), durable waits and whole-family Pause/Resume/recovery (D), and reusable observations plus deterministic evaluation from G in the [implementation plan](plans/mission-controller-20261101.md). Scoped autonomous external-write adapters (E), general isolated Python/Node workers (F), and real-model/human quality acceptance remain separate work. Existing exact approvals and current/snapshotted tool access remain authoritative. Unsupported resource bounds are shown as unavailable and refuse dispatch when configured.

## Contract and acceptance

The goal, source-bound required outcomes and their checkers are distinct from the working plan. Model refinements may add outcomes and preserve every existing predicate; only an explicit owner revision can change scope. Owner-form criteria are retained in the owner source alongside the goal. Every version remains recorded. Empty criteria cannot pass.

Supported checks bind real successful source/command/teammate receipts or exact private files. File content/hash checks reopen the current bytes. Research and document semantics use a separate bounded reviewer call with a fixed completeness/source/limitations rubric and no tools. The reviewer is a separate call/context using the frozen run provider and model; it can be the same model as the author. It sees the owner contract, exact saved document extracts, final response and actual retained source observations. Missing, truncated, unreadable or contradictory evidence fails closed. A source-read receipt alone does not certify a claim. A model assessment is recorded as such; it is not a mathematical proof or a guarantee of strategy quality. Unsupported human-acceptance criteria remain Needs attention.

Progress is the fraction of verified required outcomes, with one reserved final acceptance outcome. Actual file creation/edits refresh matching mechanical checks immediately. `mission_submit_result` can bind an exact file/source receipt to a rubric criterion and request a bounded independent milestone review; unchanged submissions are assessed once. Milestone assessments bind the current contract digest and that criterion's exact evidence subset, so unrelated later evidence does not erase a valid milestone. Changed criteria/evidence cannot reuse stale acceptance. Plan steps, elapsed time, tokens and tool counts do not increase progress. With two requirements, verified milestones show33% then66%; only the serialized final **Achieved** commit shows100%. The label counts the two requested outcomes separately from final acceptance. Final acceptance still reviews the entire goal and repeats current file and required-child checks after owned processes drain. A completed run, an exit code or a bot's assertion cannot set Achieved.

While acceptance is pending, the current-work caption also reports actual coordinator model steps, successful actions and source-read receipts. These are observed activity counts, separate from verified progress; a research task can have many reads and still have zero accepted outcomes.

Final response evidence uses a48,000-byte aggregate packet. If the answer explicitly references observed URLs/private paths, only exact matching observations enter that packet; otherwise it considers all observed sources. Omitted uncited observations are counted and cannot support extra claims. Missing, shortened or omitted selected content is marked partial and cannot pass coverage. Identical response content shared across rubric criteria is supplied to the bounded reviewer once while every original criterion/evidence identity remains checked. Oversized or partial review input becomes Needs attention with the answer preserved, rather than a raw serialization failure or repeated author attempts. The same unchanged failed acceptance input is not reviewed again within that run; changed evidence/output or a new owner-admitted episode can receive a new assessment. These bounds preserve independent acceptance and grant no action authority.

## Controls, results and recovery

**Add direction** uses the existing safe model-boundary guidance queue and preserves the contract and permissions. Revision checks and guidance admission commit together. Current questions, approvals and private browser handoff share the same exact run/prompt/generation identities in chat and Mission; answering one surface invalidates the other. Only the owner-bound coordinator gets interactive Mission controls. Assigned children keep their own tool/capability snapshots.

**Pause** first commits a durable admission gate. The page shows Pausing while an already admitted bounded action drains; no new work is admitted. At a safe checkpoint, owned processes/handles are closed, task slots are released and the Mission becomes Paused. Pause invalidates the family’s old question/approval/browser prompt identities; it is not approval or successful completion. **Resume** rechecks the complete retained family before admitting any member: execution owner, contract, current participant/provider identities, original snapshots, queued-child targets, capacity, resources and unknown effects. Saved model/reasoning, output/context/catalog settings and capability snapshots remain attached to their original work. Missing or unsafe continuations stay Needs attention. An assigned child’s participant name opens its existing bot chat, where its exact current approval can be reviewed; stale prompts cannot authorize the resumed action.

**Save a wait** supports a timer or an existing exact private file change. File observations recheck current and saved Files access and private-path/byte limits; unchanged content does not wake the model. A read failure becomes attention rather than a fabricated change. The model can also wait on exact delegation IDs from its own episode. Each one-shot wait retains a deadline, cursor and deduplicated wake identity. Sleeping frees execution capacity after the safe boundary and does not spend active model/tool time. An expired wait or a clock rollback cannot silently resume. These watches create no recurring external API grant or write permission. Saved waits show their reason, next check and expiry; Resume explicitly overrides a pending condition after preflight.

**Stop** commits durable cancellation before aborting the root and its owned children/processes. It dominates Pause, Resume, saved wakes and queued work; no queued child can dispatch after Stop. Archive applies only to finished Missions. **Try again** starts a new attempt only when work is settled and prior effects are known; unknown effects require attention. **Change goal** is an explicit owner revision, clears current acceptance and preserves earlier versions/results. Ordinary retry and goal replacement are unavailable while a durable continuation is saved. Dashboard links active/paused goals and those needing attention, including resource exhaustion and expiry. Owner goal, limit and wait forms pin their revision and preserve drafts after conflicts or an uncertain response.

Real created files are saved as immutable private blobs immediately after successful tool receipts. **Download saved result** returns those hash-checked bytes through the authenticated Mission-specific route. Later workspace changes cannot substitute a different download. A saved partial file remains downloadable without claiming the whole goal passed; only exact file versions in accepted evidence receive goal acceptance. Historical files and acceptance receipts remain recorded. No model URL creates a file card.

Recovery retains the same Mission/run/episode identities, original checkpoints, denied-call history, required-child checks and repair lineage. A whole saved family is preflighted together. Known completed child work is reconciled and rechecked; pending children reattach to their exact retained identities instead of being recreated. Undispatched queued intents still need their original target/provider identities. Unknown effects without a supported reconciliation path, changed access/providers, missing children or unsafe checkpoints remain Needs attention. Restart never supplies approval or blindly repeats a side effect. A new owner-requested attempt retains previous episode safety evidence, usage and files and must inspect existing destinations before new work.

## Mission effort

Effort controls the total work allowance for the whole Mission, including coordinator, children, failed attempts, retries, compaction and verification. It does not change the model's reasoning setting, capabilities or approval policy. Version1 profiles are Engine-owned:

| Effort | Model calls | Token allowance | Tool calls | Delegations | Parallel teammates |
| --- | ---: | ---: | ---: | ---: | ---: |
| Low | 12 | 500,000 | 40 | 1 | 1 |
| Medium | 32 | 1,500,000 | 100 | 3 | 2 |
| High | 80 | 4,000,000 | 250 | 6 | 3 |
| Ultra | 160 | 8,000,000 | 500 | 12 | 3 |

Model/tool/delegation dispatches reserve atomically against the shared ledger. Tokens use reported provider usage when complete, otherwise a local request/output estimate. These are initial product allowances requiring real-model calibration, not provider billing, subscription quotas, HTTP fanout limits or guaranteed token ceilings. An admitted provider call can report an overrun; it remains counted and blocks further work. Existing strict resource limits remain separate and fail closed on unsupported paths.

At about80% of model/token/tool allowance, the Engine enters finishing guidance and refuses new research or delegation while permitting retained-result reads, collection and final output. Two model calls,20% of token allowance and five tool calls are held inside the total for synthesis and acceptance. Finishing never relaxes the goal. If the remaining allowance is insufficient, the whole family pauses safely as **More effort needed**, retaining files, partial text and original checkpoints. **Increase effort and continue** keeps all prior usage and resumes the same work after whole-family preflight. **Finish with available results** ends as Partial, never Achieved. Effort changes use exact revision checks and cannot reset consumption. Existing Missions without an effort profile retain their old policy until an owner changes it.

The budget meter is separate from verified progress. The four-position picker supports keyboard arrows and named buttons; detailed allowances are collapsed by default. Medium is restored for a new Mission even after a previous Ultra selection. Older technical controls remain under **Advanced resource limits**.

## Resources and prices

**Resources** shows shared Used, Reserved, Unknown and Remaining amounts, supported-action readiness and **Edit limits**. Limits apply to the entire Mission, including descendants, retries and goal revisions: tokens, modeled USD, API requests, tool calls, active tool/model milliseconds and an absolute deadline. Empty fields have no explicit ceiling. Resource admission reserves before dispatch and keeps final-review headroom. Owner edits use the current revision and never erase existing consumption or unknown liabilities. Promotion imports known use and outstanding reservations once. A proven undispatched reservation can be released; a possible dispatched effect becomes unknown after failure/restart and is not refunded. An observed overrun remains recorded and blocks further work and final success.

These are local admission/accounting controls, not provider billing guarantees, subscription balances, CPU quotas or OS isolation. Used amounts may be partial observations. Unknown displays **Unknown** when the actual amount is unbounded; a held reservation is not its upper bound. Missing or subscription pricing is never zero USD. The absolute Mission deadline does not reset during waits, Pause, retries, revisions or restart.

Supported boundaries are deliberately narrow:

- Token and modeled-money admission require native OpenAI Responses or Anthropic Messages, an exact saved provider catalog/provider-error context bound and a forwarded enforced output ceiling. Owner window guesses and arbitrary compatible protocols are insufficient. ChatGPT requested output is not provider-enforced, so affected token/money bounds are unavailable.
- Native direct inference requests are admitted separately for author, compaction, memory/study and independent review calls; optional first-step intent recognition shares the first author call and adds no separate provider request. ChatGPT credential/metadata/home-renewal traffic can fan out, so its request ceiling is unavailable and uncapped network totals can remain unknown. A model-call count must not be presented as the complete HTTP count.
- Host commands, browser/search/integration calls and study paths with unbounded remote fanout refuse affected request/token/money ceilings. This is an unsupported-bound refusal, not a grant or a blanket ban on an otherwise permitted tool. The outer tool-invocation limit remains distinct from requests made inside it.
- Active tool/model time is charged elapsed wall time, subtracting validated owner approval/question/browser and dependency waits. It is not CPU use. Native inference and the existing bounded document worker support time admission; an unbounded host action, owner wait or private file watcher refuses an unsupported active-time ceiling. Cleanup can overrun and that observed time remains charged. Durable sleeping time itself is not active work.

Modeled money additionally requires an operator-supplied, versioned USD price schedule. Tupies bundles no invented price rates. Anthropic monetary admission requires explicit cache-read and cache-creation rates as well as ordinary input/output rates; admission uses the highest applicable input/cache rate and settlement records reported segments. Calculated cost remains an estimate, never a provider bill.

An operator may supply `missionPricingFile` to `createStudioServer`, or set `STUDIO_MISSION_PRICES_FILE` to a canonical absolute file path before startup. The file is read once; there is no hot reload, owner API or model-controlled pricing setting. It must be outside the entire runtime tree and model-editable workspace/skill/proposal paths: a single regular file (no symlink/hardlink), owned by the current user or root, without group/world write access, with trusted non-symlink directory ancestors. Invalid or stale configuration refuses startup rather than guessing prices. This documentation does not install a price file or change a running engine.

The strict JSON object contains only `schemaVersion` (integer 1) and `schedules` (an array), at most 100 rows and 64 KiB. Every row requires `connectionId`, `type`, `baseUrl`, `model`, `version`, `currency:"USD"`, `inputMicrosPerMillion` and `outputMicrosPerMillion`; optional fields are `cachedInputMicrosPerMillion`, `cacheCreationMicrosPerMillion` and the exact `connectionIdentity` hash. Rates are nonnegative safe-integer microUSD per million tokens:1,000,000 microUSD is 1 USD. Supply actual verified operator rates. Connection/provider/base URL identities must match the current engine; each price applies only to its exact configured model key, which need not already appear in the startup catalog; empty `baseUrl` is valid only when the actual connection has none. Unknown keys, duplicate schedules and ChatGPT subscription rows are rejected. The engine derives the trusted operator source. The first known/unknown/subscription price choice is frozen per run; its continuation keeps that version, while a new owner-approved run/attempt may use a new startup schedule.

## Saved approaches and bounded context

**Saved approaches** retains bounded observations from actual settled episodes, including failures, blocked/stopped work and unknown effects. Model descriptions may supply assumptions, steps, applicability, failures and limitations; only the Engine derives observed outcome, checks and exact evidence identities. Historical acceptance applies to the original contract. Changed goals, evidence or access do not leave a trusted method behind: even matching metadata requires applicability, permission and actual source checks for a new task.

**Review approach** reads an exact ID/digest. **Use in chat draft** opens an unsent owner-chat request for explicit scoped reads; it does not start a Mission or inherit tools. **Suggest skill** prepares inert arguments for the existing owner-reviewed skill proposal path; nothing is assigned automatically. **Prepare Brain note** opens a draft for the existing Brain permission/write path, requiring a current read/hash before replacement. Imported prose remains untrusted reference data. Export does not transfer credentials, runtime checkpoints, grants or execution authority.

Each Mission retains up to eight approach records, each bounded to 12,000 bytes before its digest, with explicit pruning/omission counts. Search scans at most1,000 scoped local Missions and eight records each, returns at most five summaries within its character budget, and rejects invalid/tampered records. Exact detail reads page at 4,000 characters. Working context keeps the current contract/outcome identities, blockers and bounded evidence/results; omitted detail uses explicit reads rather than repeating the complete journal. If mandatory contract identity cannot fit, the task needs a larger context rather than losing its acceptance gate.

The deterministic evaluation in `eval/missions-runner.mjs` exercises real disposable Engine research/document/restricted-static-code/team/reuse paths plus typed wait/restart mechanisms with independent labels, file/content/event oracles and explicit denominators. False success, scripted activation, duplicate effects, interventions and unknown resource/cost observations are reported separately. Scripted intent decisions are not real-model classification accuracy. Restricted static code checks do not establish general F worker isolation. Real-model strategy quality, human usefulness and E/F acceptance remain deferred. See the [C/D/G acceptance matrix](plans/missions-cdg-acceptance-20261101.md) for exact receipts and limits.

Expired waits end their pending Pause/Resume condition and retain its canceled history. Resume cannot revive an expired episode. The owner can replace an expired resource limit, change the goal and explicitly Try again where effects and child evidence are known; recorded usage stays charged. Missing or uncertain child records remain blocked rather than being treated as completed. A real deadline expiry without a final reply uses exact blocker attention; explicit Stop stays quiet.

## Ownership, storage and limits

One pinned engine owns each Mission. The controller uses the existing Engine admission, concurrency limit and tick; it is not a second executor. Queued admission rechecks the coordinator, provider and permission identities. Removed or changed bots/providers block dispatch without discarding history. There is no automatic cross-engine failover.

`missions` and compact controller state use the existing serialized Store. Hash-addressed receipts and immutable file blobs live in private `mission-evidence/` outside model workspaces. Full backups must preserve that directory with the runtime tree. They contain plaintext task outputs and must receive the same protection as private messages/files. No automatic evidence deletion is performed. Current bounds are 1,000 Missions, a 12,000-character goal, up to 24 schema requirements (20 in model/UI admission), 256 active evidence references, 100 saved artifacts per Mission, 20 MB per file, 100 KB per response receipt, 60,000 characters per independent review and 2 MB per retained episode safety snapshot. Exceeding a bound retains partial work and refuses unsupported acceptance.

Sync carries only an allowlisted presentation document: goal, actual participant names, state/progress, compact result text, safe wait timestamps, owner engine and freshness/revision. It excludes executable Mission state, prompts, approvals, grants, resource/price ledgers, approach records, raw journals, file blobs and dedicated Mission canonical histories. Remote summaries are read-only and their file references cannot download another engine's private files. Both linked engines should understand Mission projections before use; older engines cannot execute them. Exact Mission approval and substantive-blocker events use the existing message preference and home delivery, with stable identities, stale cancellation and attended detail receipts. Ordinary steps, durable timer/dependency/file waits, Pause and provider waits/heartbeats stay quiet; final replies remain the only completion push. Native push contracts still open the bot conversation, where the shared Mission card links to the goal; the payload additionally carries presentation-only `missionId`.

The `missions:false` Engine option disables new admission and model recognition while preserving existing rendering and Stop. It is an operator/test option, not a new owner-granted capability. [API](api.md), [verification](verification.md) and the [plan](plans/mission-controller-20261101.md) describe the boundaries and acceptance evidence. The VPS installation below is separate from source and native-app verification.
