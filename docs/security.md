# Security and execution permissions · 0.5.0


## Prompt injection: Engine responsibility

The Engine owns authorization; the model provides an additional, fallible layer of instruction following. Treat an attack as successful at steering the model when testing the permission boundary. External documents, web pages, images, skill descriptions, memories, summaries and teammate replies cannot supply approval identities, enable tools or change the bot's assigned capabilities.

New tasks keep core-memory text, assigned skill descriptions and teammate profiles out of the system message. They enter the lower-priority turn context as an explicitly untrusted JSON reference snapshot, with angle brackets escaped, frozen for that task and retained across continuation checkpoints. The system and summary instructions preserve the origin of source instructions instead of presenting them as owner requests or approvals. This separation and wording reduce instruction confusion; they are not an execution sandbox or proof that a model will ignore every injection. Old continuations retain their saved prompt snapshots.

`test/prompt-injection.test.mjs` deliberately makes a fixture model obey injected content. It verifies exact shell approval, denial/replay refusal, rejection of a model-authored approval argument, disabled tools, private workspace paths and protected Git configuration. It also checks poisoned memory/skill/team data placement and the deterministic compaction handoff. No live-model attack success rate is claimed.

**Autonomous web access remains enabled by owner choice.** `http_fetch`, keyless search and ordinary fresh-profile browser navigation retain their existing behavior. A public URL or search query can carry private text; public-address/SSRF checks and known-secret redaction cannot prevent all such exfiltration. Source text can also corrupt an answer or poison ordinary Balanced notes/files without violating an existing permission. Approved host commands have service-account access. Scope tools, integrations, teammates and retained browser sessions to the actual task; use Strict policy for exact review of local writes when needed. Future owner-issued scoped egress grants and OS process isolation are separate work, not protection supplied by this change.

The boundary follows [OWASP prompt-injection prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html): authorization and least privilege belong outside the model. Prompt filtering alone cannot establish safety.

## Optional isolated tool workshop

[Tool workshop](tool-workshop.md) is a separate owner-only capability, disabled for existing/default bots. Only the bounded QuickJS/Wasm paths for local tools and Engine candidate pure-module tests permit autonomous contributed-code evaluation without Terminal approval. It exposes no host imports, callbacks, network, files, secrets or package installation; explicit private file inputs are serialized by Engine under existing checks. Balanced may store tested immutable packages and local improvement proposals; Strict requires exact approval. Packages cannot widen access. Existing host execution remains exact-approved. Export is owner-selected and revision-bound; authored source/fixtures still need privacy review. No automatic upload or Engine patch application occurs.

The separate owner-only Engine workshop exposes allowlisted installed source, never arbitrary host paths or runtime/private handoff files. Exact base hashes and unique replacements produce isolated candidate snapshots; source hashes and access are rechecked after validation. Fixed Node syntax parsing via stdin uses no inherited environment or candidate imports/execution. Behavioral tests use only selected in-memory modules in QuickJS/Wasm; no host modules, dependencies, network or filesystem callbacks exist. Current/snapshotted access, Strict approval, Stop, size/concurrency limits and bounded engine-local storage apply. Model arguments cannot supply trusted verification. Export requires owner review of exact source edits/fixtures; independent maintainer rechecks never apply a patch. Pure-test evidence is not full Engine/build/security evidence. An operator-only container verifier now requests/checks pinned-image, non-root, no-network/no-host-mount, seccomp and resource isolation with exact-job cleanup; it exposes no bot/HTTP execution capability. Its real container boundary is exercised separately on disposable Linux CI; Docker/Podman is not installed on the development Mac. Guest code can interfere with guest results, so receipts are diagnostic evidence rather than security attestation or installation authority. See [Tool workshop](tool-workshop.md#operator-container-verification-source-only) for the fixed policy, platform-specific receipts and remaining acceptance limits.

The workshop API gateway adds no guest networking. `workshop_read_api` requires exact approval of one assigned owner-configured REST GET, its parameters/local input, tested package and connection configuration/credential fingerprint. It needs Workshop and Integrations in both current settings and the task snapshot. Engine applies the normal integration DNS/destination/redirect checks, a 64 KiB response limit and a 20-second network deadline, redacts known credentials and passes JSON into the pure guest. Revocation/configuration changes discard unfinished results; Stop cancels transport/computation. GET is not a guarantee of no service-side effects or charges, so automatic retry and standing authorization are deliberately absent. No model-supplied identity or package can authorize dispatch.

`workshop_poll_api` adds a separate owner-approved bounded-read grant. It is scoped to one exact request/package/configuration, task family, chosen bots, finite count, interval and deadline. The Engine-local `workshop-grants.json` ledger is outside model workspaces, synced documents and contribution exports. Reservations commit before dispatch; failed/uncertain attempts consume budget and block reuse, including after a receipt-write failure. Activation follows the exact owner approval commit; pending records authorize nothing. Revocation aborts in-flight use, denial also blocks the equivalent read/poll alias, and process restart invalidates all old authority. This exception never applies to generic integration calls, writes, money transfers, Terminal, browser actions or model-generated grants. Limits count requests, not actual API billing.


Tupies is a single-owner self-hosted service. Its control plane is password protected and binds loopback by default. A first-use token from the terminal gates password creation. Passwords use scrypt; server-side sessions use random HttpOnly/SameSite cookies. Mutating browser requests require a session-specific CSRF token. Host and Origin checks, restrictive script policy and static-file boundaries reduce browser attack exposure. API responses are never cached by the browser (`no-store`) and are never compressed, which keeps response sizes from leaking secrets; static application code is compressed and revalidated by ETag. Unauthenticated sign-in and pairing limits key IPv6 clients by /64 and keep fixed-size tables, so a flood of new addresses cannot exhaust memory or CPU. `npm run pair` talks only to a control socket owned by the same account in a private directory.

Native notifications use operator-configured APNs credentials and fixed Apple HTTPS/HTTP2 destinations. A paired iOS app can manage only its own registration through a bearer session; browser cookies, model output and linked-engine bearers cannot enroll devices or select a destination/topic. Device tokens are sealed in an engine-local `notifications.json`, outside replicated state. Current-source push payloads contain opaque routing IDs, a finite avatar identity, bot name and a bounded redacted plain-text reply preview plus routine/room name when applicable. Prompts, files and provider credentials are excluded. The iPhone’s Show Previews setting controls Lock Screen disclosure; the extension uses bundled avatars without network/key access. Both deployed engines now use v10 previews; the earlier v9 checkpoint sent generic text. Attended-chat read receipts can suppress only exact notification events; their sealed cross-engine exchange cannot authorize tasks, tools, approvals or enrollment. The native tap handler accepts only validated IDs for an already paired engine and opens a conversation; it cannot approve or execute actions. Device revocation stops new dispatches. Apple can observe delivery metadata, and an alert already dispatched may still arrive after revocation or disabling. See [iPhone notifications](notifications.md) for configuration, retries and remaining delivery limits.

The server stores provider API keys, integration credentials and ChatGPT OAuth bundles sealed with AES-256-GCM; only the full 128-bit authentication tag is accepted. The generated vault key and state files are owner-readable. Browser state omits encrypted credential fields and redacts known secrets from returned text/errors. Tokens are not borrowed from existing apps. Responses, memory, workspace files, skill resources and activity remain plaintext local data. Protect the service account, disk and backups.

## Tool boundary

The Skills catalog has a separate owner-controlled installation policy. By default, `skills_install` requires exact approval of the catalog ID, version and digest. An owner may allow compatible bundled reviewed versions for a Balanced bot; Strict still asks, both the run snapshot and current policy must permit automatic installation, and a denial cannot be overridden by a later policy change. At most three new assignments are installed per task. This standing policy authorizes package storage and assignment only, never scripts, dependencies, tool groups, credentials or external effects. Foreign metadata is not authority. See [skills](skills.md).

Bot tools are explicitly enabled by group. Terminal is off in the default group set. Manage Tupies (`setup`) is on by default and lets a bot create and change other bots, assign skills and manage any bot's routines, each only after exact approval. It cannot change the calling bot's own settings, enable Terminal, Browser or Coding, assign integrations or loosen an approval policy, so it cannot be used to widen host or account access. Under Balanced policy, a bot can read and write its private workspace, maintain its own core memory and long-term notes, and ask teammates for help (the whole team unless its settings limit it to selected teammates). Strict requires approval of each exact note write or append. Recalled note excerpts are wrapped as task data, and neither note text nor a note's file name or tags can close that wrapper. Notes are parsed in linear time, so a hostile heading or frontmatter line cannot stall the engine on recall. Notes are redacted for known credentials before writing; existing notes are only replaced with a matching content hash, and symlinks and hidden folders in the notes folder are never followed or indexed. Balanced also permits private document creation/replacement. Strict requires approval of the exact private file path and document specification or workspace contents. File deletes, learning a new skill, creating/removing a routine, script execution, terminal execution and every API/MCP tool call require approval of the exact action. A bot can also suggest changes to its own core memory and skills with `memory_propose` and `skills_propose`; a suggestion needs no approval because it changes nothing until the owner accepts it in the profile. Acceptance re-checks the recorded base (facts or `SKILL.md` sha256) and refuses an out-of-date suggestion, cited messages must be readable by the suggesting task (other people's Telegram chats are not citable from the owner's lanes), suggested text is redacted for known credentials, and a skill suggestion cannot change resources or scripts. Direct core-memory changes are limited to owner lanes. Third-party Telegram chats, rooms, routines and delegated work must propose changes for owner review; the channel-verified owner’s Telegram direct message keeps its owner-chat path.

Approval and Stop controls carry the run identity shown to the user. Approval additionally carries the prompt identity and execution generation; stale clicks are refused. There is no permanent or blanket approval option. Pending actions are interrupted on a restart and are not replayed automatically.

Inspected skill packages retain immutable source-separated identities and complete file-hash manifests. Incomplete or changed packages cannot be assigned, read, exported or executed. Approved managed scripts execute a copy of the verified package bytes in a temporary engine-local process-home folder, preventing incoming sync files from changing that execution copy. This remains host execution with the service account's permissions. Remote imports use bounded public HTTPS/DNS-pinned transport without credentials or redirects; ZIP paths, sizes, CRCs and symlink types are checked. Transient import previews are session/bot bound and limited to four in-flight/retained slots and 40 MB retained package bytes. These checks do not prove that arbitrary skill content is benign.

The owner can add bounded guidance to an active direct-chat task with exact run/update identities. Guidance enters canonical history only at a model boundary. Unadmitted proposed actions are recorded as not started; an already admitted action may finish. Approval/question publication refuses stale guidance races, and an outstanding prompt must be resolved or stopped before adding direction. Guidance cannot change model/tool snapshots, erase required checks or approve an action. Stop/restart cancels queued guidance without replay; final-success admission is serialized against new guidance and Stop.

Workspace and skill file tools require safe relative paths and reject symlink components. These checks constrain the built-in file tools. **Approved scripts and terminal commands are trusted host execution, not a sandbox.** They run as the service account with a reduced environment and output/time limits, but may access anything that account can access, including its data directory and network. An approval is meaningful only after reviewing the script/action and granting that access intentionally. Approved commands, skill scripts, background commands and language servers keep their working/project directory, but use an engine-local `process-homes/<botId>/` for `HOME`, XDG configuration/cache/data and temporary storage. Those directories reject symlinks and are outside model-editable workspace tools and workspace sync. The explicit environment allowlist omits host/provider credentials and startup variables, disables Python user-site loading and Git system configuration, and selects the private home’s Git global configuration. Git command-level overrides disable fsmonitor, hooks, credential helpers and the external-command transport. Changing `.git`, `.gitconfig` or `.gitattributes` through model write/edit tools requires exact approval even in Balanced policy.

These safeguards do not isolate an approved host process. Project configuration such as `.npmrc`, package scripts or imported code can still affect a command, and an intentionally approved command can change its own environment or access host files. Review the command and project together. Tool homes may retain state or credentials created by approved programs; include them in private backups. Credentials deliberately put in workspace files still sync as ordinary files.

`http_fetch` reads public HTTPS pages without approval. Its URL is model-chosen, so a prompt-injected model can include workspace, note or memory text in a request to a public address (known stored credentials are redacted). Remove the Web group from bots that hold data that must not leave the machine.

Use a dedicated unprivileged service account or container, restricted mounts and host network controls. Do not mount a Docker socket, a personal home, SSH keys or another application's credential directories. For untrusted third-party code, use a separate stronger execution sandbox; that isolation layer is not supplied by the process launcher.

## Attachments, documents and rich output

Selecting a composer attachment saves bytes only in that bot's private workspace. It does not call a model or parse the content. Send binds the selected files to the user message; a subsequent documents_read call can put extracted text into the chosen provider's context. Opening Preview performs local extraction on demand. Files, extracted text and document contents remain sensitive task data; private workspace means application-level separation between bots, not encryption or exclusion from the selected model provider after a read.

Admission checks actual regular files, derives names/MIME/size from the private path, rejects duplicate files and symlinks, and limits a message to five attachments/20 MB combined. Unsupported chat formats, cross-bot/escape paths and excessive files are rejected before a user message or model request is recorded. Document reads/downloads/exports are bounded to 20 MB per file. Preview and download URLs require the Tupies session. HTML, SVG and unknown workspace types are attachment-only rather than served as inline active content.

Document parsing/rendering uses child processes with a stripped environment, a 25-second wall-clock deadline, a 256 MB V8 heap limit and at most two active workers plus two queued jobs. Inspection acquires a worker slot before allocating file bytes. Workers receive bytes or a validated declarative specification, never provider credentials or workspace paths. Node filesystem permissions allow reads of application code, dependencies, fonts and package metadata; the parent handles private file access and atomic writes. Worker network APIs (HTTP/HTTPS/HTTP2, TCP/TLS, every DNS entry point, UDP and fetch) are disabled in JavaScript; Node 22's permission model does not itself restrict network access, and native modules can bypass these guards. Office archives have entry/decompression limits and reject macros, embedded executable objects and unsafe archive paths. PowerPoint chart workbooks under `ppt/embeddings/*.xlsx` are allowed only as opaque bounded data parts: they are never opened, executed or recursively decompressed. Chart previews read separately bounded XML caches or validated generated chart metadata. External linked content is not fetched.

These runtime limits reduce the impact of malformed documents. They do not constitute an OS sandbox, a hard total-process memory/CPU quota or security certification; dependencies and the host runtime still need maintenance. Legacy Office formats, macro-enabled documents and OCR are unsupported. Supported attached/workspace images are shown only to a model whose image-input capability permits them, through the bounded image preparation path. Spreadsheet output restricts formulas to bounded local references and allowed functions; formula-like CSV text is escaped. Imported formula caches are shown as cached data and may require recalculation.

Markdown is sanitized, raw HTML in replies is escaped, and code fences display rather than execute. Sanitized reply and document HTML keeps only the renderer's own `data-` attributes, never application action hooks. Chart CSV exports prefix formula-like text (including after leading whitespace) but leave numbers intact. Charts and infographics accept bounded data specifications. Mermaid uses strict rendering with external links/custom directives disabled; math uses untrusted rendering settings. Remote Markdown images do not load. Supported embedded document images are type/size bounded and sanitized again in the browser. No model-authored arbitrary HTML/JavaScript application executes in a chat reply.

The engine validates generated files and constructs their private Preview/Download metadata, rather than trusting model-supplied artifact URLs. A successful file committed before cancellation/failure remains available with explicit partial status. Cancellation does not undo committed exports or certify completion of the entire task. See [Rich chat and documents](rich-chat.md) for supported formats and limits.

## Network and integrations

Model-requested web reading is limited to bounded public HTTPS destinations with DNS/redirect checks. Provider and integration requests use separately configured service URLs, pin DNS results and refuse redirects to protect credentials. Metadata, link-local and unspecified addresses are rejected even when trusted-private-network support is enabled. IPv6 forms that reach an IPv4 host through translation (NAT64 `64:ff9b::/96`, IPv4-compatible `::/96`, 6to4 `2002::/16`) are judged by that IPv4 address, and site-local `fec0::/10` counts as private. Web tools treat a trailing dot as the same host name.

The interactive browser (`lib/browser.mjs`) is held to the same destination rules. Chrome is started with every connection going through a proxy inside Tupies. The proxy accepts only CONNECT to port 443, refuses local names, resolves the name itself, requires every resolved address to be public, and connects to the address it checked. A page therefore cannot reach the engine's own network, cloud metadata or a DNS-rebinding target. Plain HTTP and local addresses pass only with `STUDIO_ALLOW_PRIVATE_HTTP=true`, which is meant for local fixtures.

The browser also has these limits:
- No debugging port is opened (`--remote-debugging-pipe`), and Chrome exits with Tupies.
- Temporary profiles are deleted at task end and startup. An owner may retain a per-bot profile under engine-local `browser-sessions/`; it contains sensitive cookies/site storage, is outside model workspace tools and sync, and requires approval before reuse. Pop-up tabs are bounded; unsolicited downloads, notifications and permission prompts are refused, and WebRTC cannot use UDP outside the proxy.
- Chrome receives a minimal environment, without provider keys.
- Bot input, clicks, tab operations, dialogs and file transfers require exact approval with observed page/control identities rechecked before dispatch. Password, one-time-code and card fields require private owner handoff. The authenticated handoff API serializes exact-run/exact-view owner actions; inputs and pixels are not persisted or added to model history. Known private owner strings are redacted from subsequent model-facing results, and model screenshots are refused after private input in the task. Sites still receive values the owner enters.
- Uploads require Browser and Workspace, a private file path and matching SHA-256. Downloads are armed only for an approved action, bounded to 20 MB/45 seconds and atomically published without replacing an existing file. Neither transfer executes files. Missing action receipts remain unknown and are never automatically replayed.
- Pages run their own scripts and requests as for any visitor, and page text is marked as untrusted data in every result.

The Chromium sandbox stays on. `STUDIO_BROWSER_NO_SANDBOX=true` turns it off for hosts where it cannot start; that is an explicit owner decision with weaker isolation.

An integration must be assigned to a bot. Its fixed REST actions or discovered MCP schemas do not grant permissions by themselves. Remote read-only annotations and tool descriptions are untrusted metadata; all calls still require exact approval. No arbitrary stdio MCP server is launched from browser input.

## Autonomous bots

Delegation uses actual child runs. By default a bot may call any other bot in the workspace; a bot set to **Only selected teammates** may call only those bots, and an autonomous room turn only the room's selected members. Cycles, depth and total calls are bounded. A teammate's request is task context for the receiving bot, never authority: it runs with its own tools, and its reviewed actions still need your exact approval in its own chat. Child runs keep their own tool permissions and provider/workspace/memory. Parent cancellation propagates to child work. A shared room intentionally shares its task context with selected members, so choose membership as a data-sharing decision.

A model prompt is not an authorization boundary. Skill instructions, web content, tool results, remembered facts and teammate requests cannot change permissions. External actions may complete before cancellation reaches the service; a stopped task is not proof a sent message or API mutation was undone.

## Telegram ingress and replies

A channel is disabled until the operator enables it with explicit numeric chat and user allowlists. Both must match, and messages from bot accounts are ignored. Incoming text is task context, never permission to change the bot or approve a tool. No Telegram approval commands are provided. The assigned native bot retains its own permissions and budgets.

Offsets are durable before dispatch; reply intentions are durable before sending. Claimed but unconfirmed work/delivery is not automatically replayed after a restart. Token edits cancel and drain the old poll, and stale credential checks cannot mark a replacement token as verified. Replies use plain text and known-secret redaction. The token-bearing Telegram request path is never returned in public state or logs. No actual external messaging account is exercised by protocol fixtures.

## OAuth and operation

ChatGPT sign-in verifies state, PKCE, nonce and a JWKS-signed ID token against issuer, audience, expiry and selected identity. OpenAI returns to plain HTTP on 127.0.0.1. With `STUDIO_TLS=engine` the engine's port stays TLS-only. A pending sign-in instead opens a second listener bound to 127.0.0.1 alone (port 1455, or a free port when that is taken). It answers only `GET /auth/callback` for its exact loopback Host and Origin, and it closes once no attempt is pending, so it never adds a public listener. Tokens are retained server-side. Refreshes are serialized and frozen after ambiguous renewal so rotating refresh tokens are not replayed. Hosted/paid plan integration requires OpenAI onboarding beyond local OSS registration.

Operate one Tupies process per data directory. There is no cross-process storage lease, RBAC, SSO, MFA, security certification or public account-recovery endpoint. Keep a complete encrypted backup and apply operating-system/runtime patches. Desktop/mobile device actions are future work and are not silently enabled by provider sign-in.


## Browser voice and inference preferences

The microphone policy permits the same-origin Tupies page with browser permission and a user gesture; camera and geolocation remain disabled. OpenRouter speech requires explicit processing consent on each request and a sealed API-key connection whose destination is fixed to the official OpenRouter API. No keys reach the browser. The speech routes retain authentication, CSRF, Origin/Host validation, DNS pinning, redirect refusal, byte limits and cancellation. At most two synthesis/transcription operations run concurrently. Raw audio responses are type/signature checked; PCM is wrapped in WAV. CSP permits local blob audio without opening arbitrary media origins.

Dictation uploads validated mono 16 kHz PCM WAV of at most 60 seconds/1,920,044 bytes, transcribes into a draft and never sends a chat automatically. Recordings, unsent transcripts and generated audio are not persisted by the server. Browser audio caching is bounded to six entries/16 MB and cleared on navigation/sign-out; object URLs are revoked. OpenRouter and the selected upstream provider process audio/text under their own policies. Cloud errors are redacted and are not retried as paid inference.

The optional browser speech mode may use its vendor’s recognition service, disclosed before first use; Tupies receives no microphone audio in that mode. Browser read-aloud prefers local voices and requires acknowledgement for an explicitly selected online voice. Preferences remain browser-local. Send, edits, navigation/sign-out and conflicting speech actions cancel recording/transcription and ignore late results.

Chat model/reasoning changes are authorized workspace mutations, validated against current provider metadata. They do not expand tool permissions or alter an active run’s snapshot. Secret credentials remain server-side.
## Coding tools and progress data

Workspace discovery, search, paged reads and exact edits use the bot's existing private workspace boundary and reject symlink traversal. Search bounds include bytes read from skipped binary files. Exact edits require the complete file's expected SHA-256 and recheck before atomic replacement; stale or ambiguous changes fail. Balanced policy permits private edits, while Strict requires exact approval. Terminal subfolders and timeouts are included in the approved arguments; approved processes still have host-account permissions.

Plans and retained tool results are task data, never permission grants. Plans persist with the run and cannot change bot settings or complete a run themselves. Tool results are redacted before and after serialization, so a credential containing quotes, backslashes or newlines is caught in structured results too. Large tool results are redacted before a bounded memory-only cache; its identifiers resolve only in the same active run, expire at execution end and never become artifact/download URLs. Only explicitly classified reads overlap; all side effects retain ordering and approval barriers.

## Managed commands and language servers

Starting a background command requires Terminal and exact approval of the executable, literal arguments, private folder and timeout. Starting a language server requires both Terminal and Workspace plus exact approval of the selected bundled preset or custom executable/arguments and project root. These are trusted host processes using the service account's permissions. Workspace path checks constrain Tupies's file admission and returned locations; they are not an OS filesystem sandbox around a trusted language server. Do not approve an untrusted server or project-dependent executable merely because it implements LSP.

Opaque process/session handles are checked against both bot and current run. Output reads and stops cannot target arbitrary PIDs or another bot/run. The browser output route checks current-run identity; per-command Stop additionally requires matching run/remote-run identities and the normal authenticated CSRF/Origin/Host boundary. A stop action only terminates an already owned process and cannot launch new code. Output and metadata are bounded and redacted; stdout/stderr text, diagnostics, hover content and source files remain untrusted evidence. UI output is escaped text, never executable reply HTML.

Stop, run failure, runtime limits, server shutdown and successful completion drain task-owned commands and language servers before terminal state is committed. A descendant that leaves its process group can keep inherited output pipes open; Tupies stops waiting one second after the owned process exits, so Stop and shutdown still finish. Such an escaped process keeps running as trusted host execution. A final answer with background work still running fails explicitly. Restart marks unfinished records interrupted without replaying commands or trusting saved PIDs. Partial output and committed files remain evidence of actual progress; they never imply successful completion.

The LSP client synchronizes selected private source files and normalizes returned locations inside the selected private project. Server-initiated edits and arbitrary command execution are refused. The bundled TypeScript/JavaScript server is a pinned runtime dependency; model calls cannot install language servers, change process environment credentials or expand permission groups. Custom installed stdio servers remain subject to exact launch review. Use the same dedicated service account/container and restricted mounts recommended for approved terminal execution.

## Paired devices and linked engines

Apps pair with a single-use, ten-minute code and a P-256 device key, which Apple devices keep in the Secure Enclave when available. The device proves possession of its key; the engine signs the paired identity so the app can detect an impersonated server through the fingerprint in the link. Device pairing remains version 1; session exchange requires version 2. The signed UTF-8 message binds the target engine’s node id and fingerprint as well as device id, timestamp and nonce. A captured proof cannot mint a session on another linked engine. One-hour bearer tokens stay engine-local; clocks more than five minutes off and repeated nonces are refused. Missing/v1 session versions fail with an update error; there is no legacy signing retry. The updated app checks the advertised protocol and engine identity before using a pairing credential or device key.

Revocation ends bearer sessions and device-ticket web sessions on their next request. Revocations propagate to linked engines and are retained in each local security journal so a newer edit, tombstone or stale active record cannot restore a known revoked id. App-only revocation does not rotate the group key. An offline engine learns a remote app revocation when it reconnects; it cannot enforce an event it has not received. Signing out ends that bearer session without unpairing the device. Pairing and session routes remain rate limited.

On an internet address only paired apps can sign in by default: requests from outside loopback, private LAN and Tailscale ranges are refused password setup and sign-in, and a password session opened privately is not accepted there. The owner can allow the password from the internet in **Settings › Devices & sync**; failed passwords are then limited per client and paused for everyone on the internet after 50 failures in an hour, without affecting paired apps or private routes. Device sign-in counts only failures against a client address (IPv6 per /64) and limits each device separately, so strangers cannot lock out a paired device from another network. Internet password attempts are counted before the password is checked and refunded unless wrong, so concurrent guesses cannot exceed the hourly cap. This policy relies on the engine seeing real client addresses: see [deployment](deployment.md) for publishing a container without a proxy that hides them. Behind a reverse proxy the client address is the last `X-Forwarded-For` hop, trusted only from loopback by default (`STUDIO_TRUSTED_PROXY=private` for containers); a request for the public host name that no trusted proxy vouched for is treated as coming from the internet. The first device on a fresh server can be paired from the server shell (`npm run pair`) through a 0600 Unix socket in the data directory, so the password page never needs to face the internet.

With `STUDIO_TLS=engine` the engine terminates TLS 1.3 itself with a certificate over its identity key. The Apple app and linked engines trust that certificate only through the fingerprint from the pairing link, checked during the handshake before any request is sent, and an engine first reached this way is pinned: a different key, even with a publicly trusted certificate, is refused afterwards with a clear security message. No certificate authority, domain or DNS provider is involved. The certificate is valid for 46 days and renewed weekly over the same key: Apple's trust evaluation reports longer-lived certificates as not standards compliant (seen on iOS 27). The Apple app turns App Transport Security off with `NSAllowsArbitraryLoads` alone, because ATS refuses any certificate that no authority issued even after the app has matched the key; trust is decided by the app's own pinning, and engines that were not paired through their own key still need normal system trust. Adding `NSAllowsLocalNetworking` or another ATS exception would make iOS ignore that switch and break engines on public addresses. Browsers cannot pin, so they warn on such an address; use a domain behind Caddy if browsers must reach the server from the internet.

Linked engines are fully trusted peers that hold the complete workspace and credentials. Engine pairing and sync require version 2. Pairing uses fresh P-256 ephemeral ECDH, HKDF-SHA-256 and AES-256-GCM; signed transcripts bind the code, both engine identities, ephemeral keys, grant id and returned workspace/key epoch. A passive observer holding the code and public pairing transcript cannot derive the workspace key. Protect the code and TLS endpoint nevertheless: a code authorizes enrollment, so an active party that steals it could race to enroll a different engine. Link only through hosts and TLS endpoints you trust.

The home server’s local `sync/security.json` is authoritative for the current sealed group key, epoch, engine grants and revocations. Journal replacement flushes the file and containing directory before success; the plaintext `workspace.key` is a private compatibility mirror repaired from the journal. Engine removal atomically removes its grant and rotates the key. Every sync/key request rechecks the live authoritative grant; mutable synced device records cannot grant or resurrect engine access. Remaining trusted peers, including offline ones, recover the current key using a target-bound session and an individually ECDH-wrapped, nonce-bound signed response. Keys are never redistributed under the old shared key. A replica must reach the home server to revoke an engine; a secure disconnect first removes its own grant there.

Rotation protects future sync. It cannot erase data or credentials already held by the removed engine, revoke those credentials at their providers, or make restoring an older hub backup revocation-safe. After an old-backup restoration, keep the restored runtime offline and explicitly review/revoke/relink peers before reconnecting it. Preserve the full runtime and identity; a missing secure journal or identity fails closed instead of generating replacement trust. Existing v1 engine links pause after upgrade and require explicit disconnection/relinking with a new v2 link; no automatic downgrade is retained.

Unlinking never silently creates another automation owner. The engine persists a local suspension before removing its hub grant, quiesces channel requests and rejects new task admission during the transition. Retrying an unlink after lost acknowledgement requires a fresh exact nonce-bound hub-signed durable revocation proof; generic 401/expired bearer, stale or forged proof cannot clear the local link. The journal retains original revoked-engine public identities so mutable synced records cannot authorize this proof. Synced routines/channel enabled settings stay unchanged; the unlinked copy runs neither automatically until explicit owner promotion or relink. Promotion warns about duplicate independent jobs/messages and future model usage. Copied ChatGPT grants have a separate local ownership guard: no bearer use, local refresh, remote provider revocation or secret export to a different hub. Only successful fresh verified OAuth sign-in or rejoining the exact former home identity clears that guard. Enabling automation and editing provider metadata cannot transfer refresh ownership. These are application safeguards; a former trusted engine/operator already held the plaintext data and can act outside this process.

Provider secrets cross only inside sealed sync payloads and are re-sealed with each engine’s own vault key; metadata keeps keyed digests. Engine sessions can use only sync routes. App sessions cannot use key recovery or replication routes. Engine transport refuses redirects and has request deadlines. `tls=engine` requires HTTPS and the identity pin on first contact, including device QR/local-discovery links. Other engine addresses must use HTTPS, loopback or Tailscale unless `STUDIO_SYNC_ALLOW_HTTP=true` is set deliberately.

Only one engine runs routines and messaging channels, and only the home server renews rotating ChatGPT refresh tokens, so a schedule or a refresh token is never used twice. A bot can work on only one engine at a time; this is enforced through replicated presence, which has a short window during which two engines could both start the same bot. Remote changes to an actively running bot's model history wait until the task ends. Replicated file paths are validated against the skills and workspace roots, never follow symlinks, and are written atomically. See [Engines, devices and sync](sync.md).

## Local coding connections

Mac coding workers are optional trusted host processes with exact nested tool approvals. Restricted Claude startup disables project/user hooks, plugins and MCP setup. Existing account mode is explicit and references configuration without copying credentials; Azure credentials stay sealed and never enter the worker environment. Local-only setup uses proxy-aware client addresses. Publication intent is recorded before a push/PR and uncertain outcomes are never replayed. See [local coding](local-coding.md).

## Material learning storage

Native study intake uses engine-owned `study-staging/` and `study-jobs/` under the runtime data directory, outside bot workspaces and workspace sync. Source parsers run in bounded inert workers; their filesystem permission boundary excludes account state and workspaces. Image/PDF rendering uses bundled dependencies. The study model receives bounded source segments without action tools. Source statements, citations, learned notes and skill proposals cannot grant permissions.

Complete verified studies remove temporary originals and full extracts by default. Failed, stopped and incomplete studies have a seven-day recovery deadline; cleanup runs on the next engine tick or startup after that deadline. The engine removes only its verified owned staging, preserving saved knowledge and owner files. An explicit Keep a local source copy choice opts that job out of temporary expiry. These engine-local bytes and retained Brain notes are plaintext local data, covered by the same independent backup protection as other workspace content. Stopped source intake is cancellable.

Managed Brain knowledge is eligible for retrieval only when its active manifest matches the bot, note identity and actual note hash. Ordinary file/document tools cannot write its control manifest. Corrections and rollback publish concrete hash-bound revisions and preserve newer edits. Imported or edited Markdown alone cannot activate a managed revision. A source-derived Skill remains a pending proposal; acceptance rechecks the source knowledge revision and never enables Terminal or executes scripts.
