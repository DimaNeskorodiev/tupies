# Architecture · 0.5.0

Tupies is one self-hosted server and a browser client. Its server uses Node's HTTP, filesystem, crypto, process and network APIs, with bundled document and browser-rendering dependencies. There is no remote agent gateway, database service or runtime CDN dependency.

## A task through the engine

1. The authenticated HTTP API checks bot concurrency/reservations and validates selected attachment paths, actual file metadata, supported formats, count and combined size before recording a task. The display transcript retains the user text and attachment metadata; model context separately lists private file paths.
2. NativeEngine recalls the most relevant long-term notes once at task start. It builds a system prompt once per task from the bot's instructions, rules, core facts (pinned first), assigned skill catalog and team. Each step sends that prompt, the stored conversation fitted to the model's window, and a per-step `<turn_context>` with the date, run plan and recalled notes, which is never stored. Limits come from the model's window (95% usable, compaction from 90%, 272K default ceiling). Earlier tasks' tool outputs give way first, then the current task's oldest outputs, and only then whole earlier turns, while every call keeps a result. A provider's context error is compacted to its stated limit and the step is retried once. The saved transcript remains intact.

   Each run belongs to a lane. The Bot Chat (keyed by the bot id) covers the app, the owner's Telegram DMs and teammate requests. Other Telegram chats, each team room member and each routine run have their own history (`lib/sessions.mjs`). A completed run elsewhere leaves a short record in the Bot Chat. Room turns carry only the messages since that member's last turn. See `docs/context.md`.
3. Providers translates canonical messages and tool schemas into Responses, Messages or compatible requests. Response reasoning/tool identities are preserved for continuation.
4. The engine validates each tool call. Exact approvals pause execution before scripts, terminal commands, integration actions, deletes or Strict-policy workspace writes/edits/document exports. Adjacent calls from an explicit read-only allowlist can run in batches of up to four; every other call is an ordering barrier. Results are persisted in the original model call order, and cancellation drains started calls before history settlement.
5. AgentTools operates on the bot's workspace, core memory, long-term notes, assigned skill resources, public web data, scoped integrations or teammates (`teammatesFor` in `lib/engine.mjs`: the whole team by default, or the selected bots). Workspace tools provide bounded recursive discovery, literal search, paged reads and hash-checked exact edits. Managed background commands return owned handles while the model continues working; their output and status can be read or stopped. Approved language-server sessions synchronize current source content before real definitions/references/hover/symbol/diagnostic queries. Document tools extract bounded content or create real files through dedicated workers. Tool results go back to the model; failed results carry protocol error metadata. Large redacted results remain accessible through bounded current-run pages instead of depending on a shortened preview.
6. The loop continues toward a verified final response. Autonomous work has no lifetime time/turn/tool-call cap: unfinished plans, failed declared checks and running commands return to repair or waiting. Repeated unchanged observations, denied/missing access, uncertain actions or Stop can end work; explicit bounded mode can also reach its chosen budget. Partial text, process/session cards, recovery status and redacted events are available while it runs. Every finish path drains task-owned processes before persisting its terminal status. Verified document exports become run artifacts and final attachments; committed files on incomplete/cancelled tasks retain an explicit partial status.

The model does not own authorization. An external page, skill, remembered fact or teammate request cannot change permissions. Delegation creates another actual Tupies run with its own capability snapshot, shared root delegation accounting and parent cancellation. Asynchronous handoffs first create engine-owned jobs scoped to the requesting run; a capacity-aware queue starts children and status collection returns their real results. Queue acknowledgement is not successful child work. Pending jobs are cancelled with their parent and never dispatched by startup replay. Autonomous owner tasks have no implicit total delegation count; explicit budgets and room round limits are retained. Progress is mirrored without private content. Bounded execution pauses active-time accounting while waiting for a teammate; owner prompts pause its timers. Per-tool and prompt-expiry bounds remain independent of task mode.

Current source defaults to autonomous execution for chat and routines. Only explicit `limits.mode:"bounded"` applies lifetime numeric budgets; legacy numeric fields do not select bounded mode. `lib/autonomous-work.mjs` owns the policy, trusted transient-provider retry classification and progress fingerprints. Model-request retries retain the same task and inference snapshot, start at two seconds and back off to five minutes without a retry-count limit. The 15-minute total/five-minute inactivity limits govern individual model attempts. Retry never replays a completed tool. Four repeated identical work observations within twelve rolling observations stop a stalled approach; fresh call IDs or telemetry alone are not progress.

Routine preparation uses typed fixed reads/parsing/deduplication before inference, or renders a deterministic report without a model. Each I/O step enters the ordinary tool-admission path. The optional final save uses workspace-write approval, and its current bytes are checked before completion. Seen-item cursors commit only after complete success. A saved plan remains separate from these executable steps and actual receipts.

Direct owner chats and routines retain bounded redacted engine-local checkpoints. After process/browser/coding managers initialize, startup recovery may adopt only the current interrupted schema-version-2 autonomous checkpoint, with the same run ID, model, reasoning and capabilities. Current task/configuration, bot/access and provider/account identities are revalidated. Historical failures, replaced work, old checkpoints and cancelled work do not become recovery candidates. Stop records cancellation before abort. Unknown mutation outcomes block recovery; an exact completed file mutation is reused only after checking current file bytes. No old approval or expired process/browser handle becomes authority. The UI reports recovery automatically without a Continue button. These autonomous changes are installed on both operational engines as `autonomous-work-20261030`; see [Routines](routines.md).

Harness tools maintain a bounded plan on the active run and read retained tool output. Plans are persisted atomically, survive interrupted work and remain separate from run completion. A completed checklist cannot complete a run, authorize a tool or change its capability snapshot. Output retrieval accepts the exact resultId from a shortened current-run result, rather than a model-supplied filesystem path. See [Tool use](tool-use.md) for limits and workflow details.

## Native specialist learning (current source)

The native `tupies-learn-from-material` package owns learning methodology. The Learning view and direct-owner-chat `study_material` enter the existing Engine’s admission, approval, cancellation and recovery lifecycle, pinning role/focus, skill resource hashes and inference choices. They do not create a second scheduler or depend on another agent runtime. Ordinary attachment Send keeps its prior workspace/history behavior.

`StudySources` stages exact admitted bytes outside workspace/skill sync, inventories pages/timed units and supplies bounded hash-checked segments. A stripped-environment worker parses DOCX/PDF and renders/fits images with fixed resource limits. Optional visual reading calls the selected image-capable provider with no action tools. Uploaded PCM16 WAV is normalized/chunked for an explicitly configured OpenRouter transcription service with owner consent. Captions, visual interpretation and audio transcription keep their actual source/time/page identity and uncertainty; unavailable content remains a gap. YouTube frames are not sampled or described as inspected.

The study runner applies the pinned methodology and independently checks selected candidates, validates exact supporting quotes and passes only selected knowledge to `KnowledgeService`. Publication journals bind note/manifests and before/after hashes. Managed Brain revisions become retrievable only when the manifest identifies the current bot/path/hash and active state. Partial sync arrivals, external edits and superseded revisions fail closed. Ordinary workspace/document tools cannot forge publication manifests. Corrections and batch rollback use exact reviewed previews, while learned methods become pending owner-reviewed Skills; execution authority remains in the ordinary tool layer.

Originals, full extracts, prompts, active study jobs and journals remain local. Accepted knowledge and bounded provenance/evidence use file sync; shared task outcomes remain presentation only. Complete publication removes temporary intake by default. Inactive non-kept source copies expire after seven days when normal running-engine ticks or startup/list/admission runs the expiry check; active work and explicit Keep originals are preserved. Deletion does not erase protected backups or provider retention. The study layer checks committed publication before cleanup so recovery after a lost cleanup acknowledgement does not require discarded originals or repeat inference.

Current deduplication is exact, and retrieval remains lexical. Broad semantic consolidation and contradiction handling are still skill/model-assisted rather than a complete deterministic merge engine. Public miniature fixtures exercise the machinery; real-model/human usefulness and the full three-encyclopedia/ten-video acceptance remain open. These changes are mutable source, not a new operational deployment.

## Documents and browser rendering

Composer selection uploads bytes to a bot's private workspace; it does not parse the file or send it to a provider. Send associates up to five files/20 MB with the task. The bot reads relevant content through documents_read after admission. A user opening Preview invokes local extraction independently of a model request. The same authenticated workspace boundary serves preview and download URLs; these are not public share links.

The engine's standing instructions describe Markdown, chart/infographic JSON, Mermaid and math, plus the documents_create specification. The model cannot make a file card by inventing an artifact URL: the engine records only a successful creation result whose actual private path and bounded file can be verified. It also removes final download cards for files deleted later in that turn.

Document work uses at most two active child processes and two queued operations, each with a 25-second wall-clock deadline and 256 MB V8 heap limit. Workers receive bounded bytes/specifications through stdin, run with a stripped environment and Node filesystem read permissions limited to application code, dependencies, fonts and package metadata. Network APIs are disabled in the worker. The parent retains filesystem writes and commits completed exports atomically. These are application/runtime defenses, not an independent OS security sandbox.

PDF, DOCX, PPTX, XLSX, Markdown, CSV, text and JSON share the read/create pipeline. PDF reading extracts text without OCR. PNG/JPEG/WebP attachments offer a user image preview. For a model that can see images, the worker's `image` operation fits each attached image (upright, a 1568px edge, about 1.15 MP, PNG or JPEG); the engine keeps only references in the conversation and adds image parts per step. Office content previews do not reproduce full editor layout. Workbook generation caches simple local formulas where possible and requests recalculation for other accepted formulas.

Rich browser replies use local bundled libraries, sanitized Markdown and bounded declarative visual formats. Inline charts support six types; document chart blocks support bar, line and pie. Arbitrary HTML/JavaScript, diagram links/directives and remote images cannot become executable reply content. See [Rich chat and documents](rich-chat.md) for the user workflow and valid tool examples.

## State and storage

state.json holds bot configurations, provider metadata, sealed credential bundles, conversations, message attachment metadata, memory, runs and their plans/artifact metadata, rooms, routines, messaging channel cursors/claims and activity. Large tool output is retained in active-run memory after redaction: up to 250000 characters per result and 1000000 per run, with oldest-first eviction and expiry on finish. The ordinary saved conversation contains its shortened result envelope. Autonomous recovery additionally retains bounded redacted progress and completed-effect evidence in engine-local task checkpoints and `routineRuntime`, excluded from public polling and sync. Retention and aggregate-size limits can make older recovery evidence unavailable. Successful completion/cancellation removes the checkpoint; committed routine seen-item state remains local. vault.key is the owner-readable encryption key. skills/<id>/ preserves skill documents/resources; workspaces/<bot-id>/ contains bot files. Engine-local process-homes/<botId>/ holds approved tools' HOME/configuration/cache/temp separately from model workspace writes; it never syncs and belongs in a protected full-runtime backup. Atomic writes and serialized mutations protect one running process. There is no distributed lease or multi-process scheduler.

Engine-local `study-staging/` holds feature-owned originals and segment bytes; `study-jobs/` holds bounded private progress/method snapshots. `knowledge/` holds publication journals and protected earlier revisions. These are outside replicated workspace/skill roots and belong to protected full-runtime backups while retained. Active managed knowledge and its manifests live under the bot’s Brain; metadata cannot authorize execution.

Every committed mutation still rewrites the whole `state.json`, so its cost grows with the stored history. The last committed bytes double as the rollback point (a failed mutation restores them instead of deep-copying the state beforehand), each commit advances a revision counter, and run-progress commits (streamed text, work-log events) are marked local so sync does not rescan the replicated documents for them. Model context compaction measures each stored message once and copies only the retained tail. Chat and room polling return an ETag derived from the response and answer `304` while the transcript is unchanged; the browser keeps those tags in memory only, and API responses stay `no-store`. Finished replies' sanitized Markdown is memoized in the browser within a bounded budget. Static application files are compressed with Brotli or gzip once per file version and revalidated by ETag. Conversations are never trimmed, so very long histories still grow the state file and each commit; moving transcripts out of `state.json` is on the roadmap.

`sync/` holds the engine identity, the workspace key shared by linked engines, the home-server link and per-document sync metadata; see [Engines, devices and sync](sync.md). Long-term notes are Markdown files in each bot's `workspaces/<botId>/brain/` folder; their search index is rebuilt in server memory from file metadata. Messages, files, notes, skill resources and memory are plaintext local data. Only credentials are sealed. A complete data backup includes the encryption key and therefore must itself be protected/encrypted.

## Future clients and device actions

The browser calls a same-origin authenticated HTTP API; engine and persistence do not live in the client. The Apple app (`apps/apple/`) pairs with device keys, signs in with bearer sessions and hosts the same web interface for each engine, switching between them in one click. Several engines can share one workspace through the home-server sync described in [Engines, devices and sync](sync.md).

Native Mac/iOS computer actions need a separate device boundary: explicit device pairing, scoped capabilities, short-lived credentials, action-specific approvals, revocation, audit events and OS permission handling. The intended device worker should execute only a declared action authorized for its device. A model-generated command must never grant itself device or account access. Device pairing for apps is shipped; no device worker, screen-control transport or Mac/iOS action implementation is.

## Mac-local coding workers

The optional local coding coordinator owns approved external Claude runs, separate repository copies, independent verification and Azure draft PR publication. Its local account/job directory never enters sync. Codex execution and remote Mac dispatch remain unavailable. See [local coding](local-coding.md).

## Engine source candidates

`lib/engine-workshop.mjs` owns the separately enabled source allowlist, exact revision reads, focused replacements, immutable local snapshots and generated proposal evidence. `lib/engine-candidate-checks.mjs` parses JS with a fixed syntax-only Node invocation and supervises `lib/engine-candidate-worker.mjs`, whose QuickJS loader can return only selected in-memory source. No candidate module is imported by the host or applied to the installed tree. Workshop inbox/export and maintainer reconstruction share exact edits/base hashes; full Engine builds and arbitrary dependency execution remain outside this sandbox. See [Tool workshop](tool-workshop.md).
