# Qwen3.8-27B on the owner's Mac — L0 measurements, 17 November 2026

Phase L0 of the [local models plan](../plans/local-models-20261117.md). It measures how Qwen3.8-27B behaves behind the two MLX runtimes before the engine depends on it.

- **Not measured: Ollama.** The owner deferred the 17.7 GB `qwen3.8:27b` download.
- **No Tupies code changed.** The probe scripts ran outside the repository.
- **Real request parts.** The prompts used the engine's actual system prompt and the 16 tool schemas of a default new bot (about 5.3K tokens), dumped from a disposable store the same way `scripts/measure-prompt.mjs` does. They also used the actual action-review and memory-review instructions and result schemas.

## Setup

| | |
| --- | --- |
| Mac | Apple M4 Pro, 14 cores, 48 GB unified memory, macOS 26.7.1 |
| Weights | `mlx-community/Qwen3.8-27B-4bit` (affine 4-bit, group 64; 16.1 GB on disk; `model_type: qwen3_5`) |
| Runtime A | `mlx_lm.server` 0.32.2 (`mlx-lm` 0.32.4 core), defaults |
| Runtime B | `mlx_vlm.server` 0.8.0: first as the owner ran it (prefix cache off), then with `APC_ENABLED=1 APC_DISK_ENABLED=0` |
| Requests | OpenAI-compatible `/v1/chat/completions` with streaming and `stream_options.include_usage`. Model-card sampling: thinking `1.0/0.95/20/0/0`, non-thinking `0.7/0.8/20/0/1.5`. |
| Isolation | One copy of the model in memory at a time, under a watchdog that stops the server when system free memory falls below 20%. |

**Contamination in the first run.** It shared the GPU with another session that loaded a second copy of the model plus an MTP draft model. That exhausted RAM and crashed other applications. Numbers from that run are used only where a clean run agrees with them.

## Results

### Tool calls

Both runtimes return structured, streamed `tool_calls` with the `qwen3_coder` parser. Across 18 tool-calling requests:

- every call had an id and arguments that are a valid JSON object;
- no XML leaked into `content`;
- a request needing two reads returned two parallel `workspace_read` calls;
- after a `role: tool` result, the model answered correctly from it.

**No XML tool-call parser is needed** for MLX.

`mlx_lm` sometimes puts `"\n\n"` in `content` before the tool call. Tupies should treat whitespace-only text next to tool calls as empty.

### Thinking

| | `mlx_lm.server` | `mlx_vlm.server` |
| --- | --- | --- |
| Default | **On** (the chat template's default) | **Off**, unless started with `--enable-thinking` or the request sets `reasoning_effort` |
| Where reasoning arrives | `delta.reasoning` | Both `delta.reasoning_content` and `delta.reasoning`, with the **same text twice** |
| `<think>` inside `content` | Never | Never |
| `chat_template_kwargs.enable_thinking: false` | Works | Works |
| Top-level `enable_thinking: false` | **Ignored** (it still thought for 444 tokens) | Works |
| `reasoning_effort` low / medium / xhigh | Accepted; 168 / 198 / 277 tokens on a small question (one sample each; not clearly different from sampling noise) | Accepted, and it turns thinking on; 140 / 148 / 280 tokens. `/v1/models` advertises `reasoning_efforts: ["xhigh","medium","low"]` |

`reasoningOf` (`lib/providers.mjs:173`) reads only the first non-empty field, so `mlx_vlm`'s duplicate fields do not double the text. A `<think>` splitter is **not** needed for these runtimes. It remains a cheap safeguard for other compatible servers.

The control that works on both runtimes is `chat_template_kwargs.enable_thinking`.

### Prefix reuse

Without a prefix cache, every agent step re-reads the whole prompt. With a cache, the next step pays only for the new part.

| Sequence (cached tokens, time to first token) | `mlx_lm` (cache on by default) | `mlx_vlm`, APC off (owner's default) | `mlx_vlm`, `APC_ENABLED=1` |
| --- | --- | --- | --- |
| Real 5.3K prompt, repeated | 5,354 cached | 0 cached, 42 s again | 5,331 cached, 1.4 s |
| Tool result plus next step (same system and tools, new tail) | 5,197–5,235 cached → **2.0 s** instead of 44 s | 0 cached → 42 s | 4,096–5,423 cached → 0.4–11 s |
| New task: same system and tools, different user message | 5,197 cached → 3.0 s | 0 → 42 s | 0 → 42 s |
| 14.2K prefix → short unrelated request → 14.2K prefix again | 14,197 cached → **0.2 s**; the short request did not evict it | — | 14,197 cached → 0.4 s |
| 14.2K prefix plus one more turn | 14,202 cached → **0.6 s** | — | 14,197 cached → 0.9 s |

Notes:
- `mlx_lm` keeps several cached sequences (LRU) with checkpoints at the system-prompt boundary, so a new task that reuses the system prompt and tools is also fast.
- `mlx_vlm`'s APC restores recurrent state only at block checkpoints along an exact earlier sequence, so a new user message right after the system prompt missed.
- The hybrid architecture (48 of 64 layers recurrent) does **not** prevent prefix reuse in either runtime.

### Background reviews

These used the real instructions and schemas of action review and memory review (current limits: 20 s and 12 s), with about 800 prompt tokens and no cache.

| Review | Thinking on (`mlx_lm`) | Thinking off (`mlx_lm`) | Thinking off (`mlx_vlm`) | Warm repeat, thinking off (`mlx_vlm`, APC) |
| --- | --- | --- | --- | --- |
| Action (limit 20 s) | **135 s**, 1,839 tokens: `manual` | 15.2 s: `approve` | 16.0 s | 10.9 s |
| Memory (limit 12 s) | **81 s**, 1,047 tokens | **13.4 s** (over) | **14.6 s** (over) | 11.7 s |

**Quality signal.** The action review asked to approve a POST of a summary to the owner's team webhook. With thinking, it chose `manual`. Without thinking, it chose `approve` and copied the 64-character `actionDigest` as 100 characters. That violates `maxLength: 64`, so the engine's validation would reject the result and fall back to manual approval. One sample is not a rate, but it argues against relaxing the action reviewer for local models.

### Agent evaluation

#### Tupies cannot talk to `mlx_lm.server` today

Every engine request to `mlx_lm.server` failed with **HTTP 411 Length Required**: 4 of 4 cases, 0 tool calls.

- `serviceRequest` writes the body with `request.write()` and sets no `Content-Length` (`lib/provider-net.mjs:123`), so Node sends the body chunked.
- `mlx_lm.server` is built on Python's `http.server`, which refuses chunked request bodies.
- The probe scripts above used `fetch`, which sets the length, so they were not affected.

The fix is one line: send `Content-Length` (`Buffer.byteLength`) for every request with a body. It becomes L1's first item.

#### Live run on `mlx_vlm.server` with APC

`npm run eval:agent -- --mode live --provider custom`, against `mlx_vlm.server` with `APC_ENABLED=1`, with the engine as it is today:
- no reasoning parameters, so this runtime does **not** think;
- an output limit of 4,096 tokens;
- the eval's 120 s per-request limit and 10 min per case.

| Case | Result | Time | Model calls / tool calls | Prompt tokens, of them cached |
| --- | --- | --- | --- | --- |
| research-document | **passed** (5/5 checks: report written, newest values and arithmetic, source attributed) | 85 s | 5 / 4 | 25,079, 17,773 cached |
| memory-correction | **passed** (6/6: correction replaces old value, paraphrase answered, privacy scopes kept) | 90 s | 3 / 1 | 14,141, 4,255 cached |
| ask-deny | **passed** (5/5: structured question, refused delete not performed and attempted once) | 70 s | 4 / 3 | 22,617, 17,421 cached |
| teammate-partial | **time budget reached** at 10 min | 600 s | 11 / 8 | — |

Quality counters over the three scored cases:
- verified completion 3/3;
- false success 0;
- unauthorized changes 0;
- duplicate effects 0.

**Why teammate-partial ran out of time.** It delegates to a specialist. Each specialist turn has its own system prompt, so it starts cold, at about 40 s per 5K prompt tokens. Delegation and other multi-lane work is the slowest pattern on a local model. A single sample per case shows the model can do the work; it is not a rate.

## Decisions for the plan (the L0 gate)

0. **Fix the request body first.** Send `Content-Length` on every provider request with a body. Without it, `mlx_lm.server` refuses all of Tupies's requests with HTTP 411.
1. **Recommended runtime: `mlx_lm.server`, after fix 0.**
   - Prefix caching works with no flags, including for a new task on the same system prompt.
   - It is the leaner server.
   - `mlx_vlm.server` is also supported: the owner already runs it, it accepts images, and it passed the live eval as the engine is today. The setup card should recommend `APC_ENABLED=1` for it, because without it every step re-reads the full prompt (about 42 s at today's 5.3K fixed prompt).
   - Delegation to specialists starts each specialist cold. Expect multi-lane work to be minutes slower than on a cloud model.
2. **Prefix caching is a requirement, not an optimization.** Cold prefill runs at about 120–130 tok/s, so the first token of a step costs about 1 s per 125 tokens of uncached prompt.
   - Tupies must keep request prefixes stable: fixed system prompt, stable tool list, turn context only at the end. It largely does already (`docs/context.md`).
   - Connection test and status should detect "no prefix reuse" by sending the same short prompt twice and comparing `usage.prompt_tokens_details.cached_tokens`. If there is none, warn.
3. **Time to first token.** A cold 24K-token step takes 3.5 min before the first token, and a compaction-sized prompt takes longer.
   - The plan's separate first-token limit (15 min) and total limit (45 min) stand.
   - The 120 s idle limit would kill any cold step above about 14K tokens, so it must not apply before the first token.
4. **Window and memory.** A 76K-token cold prefill on `mlx_lm` with default settings pushed a 48 GB Mac to 18% free memory.
   - **Default the local window to 32K**, not 64K.
   - Allow 64K, warning about memory on Macs with 48 GB or less.
   - Re-measure with a smaller `--prefill-step-size` (512) before recommending larger windows.
5. **Thinking control.** Send `chat_template_kwargs: {enable_thinking: …}`, which works on both runtimes.
   - Map the slider's off position to `false`.
   - Map low / medium / xhigh to `reasoning_effort`, keeping `enable_thinking: true`.
   - `reasoning_effort` showed no clear effect on length at this sample size; re-check on agent tasks.
6. **Reviews.**
   - Thinking on makes reviews take 1.5–2+ minutes.
   - Thinking off brings action review to 11–16 s, near its 20 s limit. Memory review still takes 12–15 s against a 12 s limit.
   - So, on local connections:
     - thinking off for memory and skill review, with a **30 s** limit;
     - action review on the task model with thinking off and a **45 s** limit. A schema-invalid result is manual approval, as today.
     - L1 should run one A/B of action-review decisions with thinking on and off on a small fixed set before choosing thinking off for action review.
7. **Queue.** Both runtimes batch decoding: two concurrent requests finished in 16 s versus 14–15 s for one.
   - A strict one-at-a-time queue is not required for correctness.
   - Keep a small per-host limit (2) with interactive work first. Prefill is compute-bound and two cold prefills would each take twice as long.
8. **Sampling.** `mlx_lm.server` defaults to `--temp 0.0` (greedy). Send the model-card sampling explicitly, as planned.
9. **No XML tool parser, no `<think>` splitter needed** for MLX. Treat whitespace-only `content` next to tool calls as empty.
10. **Ollama** remains unmeasured. Repeat this probe after `ollama pull qwen3.8:27b`, focusing on `num_ctx`, native `/api/chat` tool calls, thinking control and prefix reuse.

## Reproducing

The probe used two scripts, outside the repository, that are not checked in:
- one dumps the real request parts;
- one sends the requests.

To reproduce, copy them into `scripts/` with a `--base`/`--model` interface. Run one server at a time, with a memory guard.
