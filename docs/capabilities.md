# Tupies Engine capabilities

Tupies 0.5.0 runs independently. Model calls go directly to the selected provider. Bot state, the model/tool loop and task orchestration are Tupies-owned; there is no Hermes gateway dependency. This table describes current source; [verification](verification.md) records tested builds and deployment status.

| Capability | Implemented behavior | Boundary |
| --- | --- | --- |
| Agent loop | Repeated model/tool turns, live partial text, progress events, usage, stop and durable final status | Default 20 model steps, 60 tool calls and five minutes per task. Time spent waiting for a teammate does not count toward the five minutes (the teammate's run has its own limit), but no task, teammate waits included, runs longer than 30 minutes. Waiting for the owner's answer to a question pauses both limits; an unanswered question expires after 24 hours. A long turn shortens and then omits its oldest tool outputs to fit the working context instead of failing. Reaching a limit preserves work and reports an incomplete/failed task. |
| Model providers | OpenAI Responses, Anthropic Messages, xAI, OpenRouter, Ollama and compatible APIs | Account keys, model availability and billing remain provider-controlled. Model discovery does not spend inference tokens. |
| ChatGPT / Codex plan | Tupies-owned PKCE sign-in, signed identity verification, sealed tokens, serialized renewal, direct Responses requests | Eligible account and plan permission required. Local/open-source self-hosted flow; paid or remotely hosted products require OpenAI onboarding. |
| Chat model and reasoning | Per-bot chat menu selects a provider-catalog model or restores the shared default. Reasoning levels come from explicit supported metadata. | Applies to the next task; active task continuations retain their original settings. Unknown capabilities keep provider-default reasoning. |
| Voice input and read aloud | OpenRouter recorded dictation, AI reply playback, model/voice selectors and three-model previews. Eleven v4 Turbo/Scribe v2 defaults; browser speech remains optional. | Explicit cloud consent and an OpenRouter API key/credit balance required. Recordings are bounded to 60 seconds; browser recording support/microphone access required. No continuous realtime conversation or subscription audio entitlement. |
| Bot identity | Role, instructions, model, selected skills, tool groups, memory, private workspace and persistent conversation | Provider accounts can be shared without sharing bot conversation or memory. File isolation is an application boundary. |
| Cushion companions and interface | Pearl desktop and iPhone layouts with a selectable catalog of 24 cushion companions. Compact views use portraits; welcomes/profile heroes can use full-body artwork. All companions have restrained body motion; the twenty additions also use rendered blink/look/wave poses. Existing bot names and saved activity palettes are preserved; fresh workspaces still seed a chief-of-staff bot named Roki. | Avatars are presentation, not task telemetry. Paused bots and Reduce Motion use idle artwork; offscreen/hidden-page animation suspends. Phone follows system light/dark appearance; desktop uses the selected light pearl theme. Physical-device accessibility and motion review remains separate from browser fixtures. |
| Memory | Private core facts/pins with task relevance, explicit truncation and provenance/correction revisions; Obsidian-compatible notes; bounded blending of facts/notes/scoped conversation excerpts; opt-in engine task observations | Local plaintext and lexical ranking, no vector dependency. At most four notes/about 4000 characters per recall, up to three refreshes per task after plan/context changes. Unattended/third-party/delegated core changes require review. Episodes default off, exclude private lanes and Strict writes, and make no extra model calls. See `memory.md`. |
| Questions | In a direct Tupies chat a bot can ask one to three questions with `ask_user` (choices, multiple choice, free text). The task waits, the chat shows a question card with Send answer, Skip and Stop, and the Dashboard lists it under **Needs you**. The answer goes back to the model as structured data and the chat keeps a readable record. | Direct Tupies chats only: not team rooms, routines, Telegram or delegated work, where the tool is not offered. At most 20 question prompts per task. An answer is task data, never approval. A restart while waiting interrupts the task, as with approvals. |
| Conversation search | `session_search` (ranked lexical search with word forms, role and date filters, paging) and `session_read` (a message with its neighbours, paged) over the bot's stored display transcript, which stays complete after compaction. Part of the Memory tools. | The Bot Chat, team rooms and routines search the bot's history apart from Telegram chats with other people; such a Telegram chat searches only itself. The current task's own messages are left out. Not semantic or vector search. |
| Owner transcript search | Visible desktop/phone search, Cmd/Ctrl+K, bot/room scope, excerpts and exact-message navigation. Unsent page-session drafts remain intact. | Local display transcripts, including hidden bots; no model call. Bounded lexical scan of 20,000 messages/8 million characters, with an explicit partial-search notice. |
| Direction during work | Add text guidance to the same active direct-chat task; idempotent receipts and queued/applied/cancelled transcript status. Superseded unadmitted model actions are skipped. | Eight updates/32 KB per task. An admitted action can finish; prompts must be resolved first. Permissions, original checks and model/capability snapshots stay fixed. Stop and revise to abandon a required outcome. |
| Run history | Last 50 finished tasks per bot, with status/usage/files, bounded work receipts and declared mechanical-check results; Recent tasks has an optional evidence disclosure | Engine-local, never synced. Model receipt reads respect conversation privacy. Checks certify only declared mechanical properties, not every natural-language requirement. |
| Files and attachments | Private per-bot folders, file management and composer attachments associated with the message on Send | Up to five files and 20 MB combined. Selecting files stores local bytes; it does not call a model or parse them. Private paths, actual file metadata and supported formats are validated before task admission. |
| Workspace coding tools | Recursive filename globbing, literal text search, paged UTF-8 reads with a content hash, whole-file writes and exact text replacements | Paths remain inside the bot's private workspace; symlinks and special files are refused. Searches and pages have explicit limits. Edits require the expected file hash and reject stale or ambiguous replacements. |
| Outcome checks and recovery | Private-file predicates, actual command/source/teammate observations, final rechecks, error categories and bounded safe-read recovery | Criteria are model-extracted candidates. Required failed checks/deliverables prevent success. Denied/uncertain actions are not replayed; no automatic command retry. |
| Background commands | Approved commands return a process handle while the bot continues; paged merged output, exit status and per-command Stop are available through tools and chat | Terminal must be enabled. Four commands per task, eight globally and 20 retained process records per run; 250000 output bytes per process. A command timeout is at most 30 minutes and still obeys the task's normal runtime limit. Stop/failure/finish/shutdown drain task-owned commands; restart never replays them. A final answer with commands still running fails explicitly. |
| Code intelligence | Real stdio LSP definitions, type definitions, implementations, references, hover, document/workspace symbols, incoming/outgoing call hierarchy and diagnostics, synchronized with current private files. Bundled TypeScript/JavaScript server and approved custom installed servers | Launch requires Workspace plus Terminal and exact approval. Queries use an owned session and remain in its private project; unsupported capabilities and diagnostic freshness are explicit. Call hierarchy uses opaque session item handles and rejects source revisions changed since preparation. Trusted language servers use host permissions, not an OS sandbox. No automatic package installation, arbitrary LSP command execution or server-requested file edits. Sessions end with the task. |
| Parallel tool reads | Up to four adjacent, explicitly classified read-only calls execute together; results return in the model's original call order | Every mutation, approval, integration call and delegation forms a barrier. Stop aborts and drains started reads before final history settlement. Normal task/tool budgets still apply. |
| Task plans and output paging | Durable per-run structured checklist and paged retrieval of large redacted tool results held in active-run memory | Plans have at most 20 steps and one active step; they do not grant permissions or mark a task successful. Result pages contain at most 12000 characters. Retention is capped at 250000 characters per result and 1000000 per run, evicts oldest results first and expires on finish. Full retained output is absent from public polling and has no extra persistent copy. |
| Image understanding | Attached PNG, JPEG and WebP images are fitted in the document worker and shown to models that can see images, through each provider's own image input. With Workspace tools and an image-capable model, `workspace_image` opens a private workspace image mid-task through the same bounded worker. The newest five images in a conversation stay visible for follow-up questions. Per-connection **Image input** setting (Automatic / on / text only); Chat options and the composer say whether a bot's model sees images. | Capability comes from the owner's setting, the provider's catalog or a known family; unknown models are text-only. A refused image is retried once without images and the model remembered as text-only. Private paths, file metadata and supported formats are checked before workspace-image reading. No separate OCR engine or image generation. |
| Document reading | PDF, DOCX, PPTX, XLSX, Markdown, CSV, UTF-8 text and JSON through documents_read and local previews | Text extraction is bounded; PDFs need extractable text. No OCR of scanned PDFs, legacy Office binaries, macros or embedded executable objects. Office previews show content rather than exact editor layout. |
| Document creation | Real PDF, DOCX, PPTX, XLSX, Markdown, CSV, text and JSON exports through documents_create | Up to 20 MB per file and 150 KB model tool arguments. Successful exports become private Preview/Download cards automatically. Balanced permits private creation/replacement; Strict requires approval of the exact path and specification. |
| Rich chat | Markdown, tables, highlighted code, copy controls, math, Mermaid, charts and infographic cards | Declarative bounded formats; no arbitrary HTML/JavaScript execution or remote image embedding. Inline charts support bar, line, area, pie, doughnut and scatter with PNG/SVG/CSV downloads; document charts support bar, line and pie. |
| Spreadsheet output | Named sheets, typed cells, safe local formulas and embedded chart images with their source data | Simple formula results are cached when calculable; other accepted formulas require recalculation in Excel. Imported cached results may be stale. CSV formula-like text is escaped. This is not a complete spreadsheet calculation engine. |
| Skills | Hermes-compatible SKILL.md, progressive instruction/resource reads, full resource-byte import/export and approved script execution | Bounded frontmatter parser; scripts use installed Node/Python/Bash and their available dependencies. Symlinks and unsafe relative paths are rejected. |
| Learning and natural-language routines | Approved skills_create saves and assigns a reusable SKILL.md; approved routines_create schedules a bot-owned recurring task. `memory_propose` and `skills_propose` suggest changes to the bot's own core memory and skills (including edits to an assigned skill) for the owner to accept, decline or later undo in the profile's **Learning** tab, with an optional prepared daily review routine | skills_create cannot overwrite existing skills; changing one goes through a reviewed suggestion. Scheduling future model use requires exact approval; bots can list/remove only their own routines. Suggestions change nothing until accepted; one made against facts or a skill that changed since is refused as out of date, and undo applies only while nothing newer changed it. See `memory.md`. |
| Tool permissions | Per-bot tool groups and exact-action approvals | Balanced policy allows private workspace writes, exact edits and document exports/replacements; Strict asks for approval of their exact arguments. Deletes, scripts, terminal and integration calls require approval. Harness plan/output tools cannot expand enabled tool groups. |
| Web reading | Bounded public HTTPS fetching with DNS/address/redirect checks | No general search-engine subscription. Web data is untrusted task evidence. |
| Read-only browser | The opt-in **Browser** tools: a task opens public HTTPS pages in its own headless Chrome or Chromium, reads a text outline of what scripts render (links and buttons get references such as `[e3]`), follows links, expands sections, scrolls, reads full text and goes back. A bot whose model can see images can take a screenshot; it is saved under `browser/` in its workspace and shown to it. | Needs Chrome, Chromium or Edge on the engine (nothing is downloaded; `STUDIO_BROWSER` names another path). Same network rules as web reading: HTTPS on port 443 to public addresses, resolved and pinned by Tupies. No typing, sign-ins, uploads, downloads or pop-ups; each task gets a fresh profile that is deleted when it ends. Pages may still send their own requests, as when anyone opens them. At most one browser per task and two at once. Main frame only; content inside iframes is not outlined. |
| Web search | Keyless DuckDuckGo HTML/Lite discovery through the engine public HTTPS transport; bounded URL/title/snippet results and explicit challenge/rate-limit/layout failures | Web tools required; queries go to DuckDuckGo and results need source verification. The owner may select an assigned SearXNG, Tavily or Brave fallback for availability failures, with exact integration approval. Genuine empty results, policy refusals and cancellation do not trigger fallback. Private SearXNG setup is optional and separate; see [setup](searxng.md). |
| API integrations | Owner-declared REST actions, API credentials, GitHub/Slack templates | Fixed paths and bounded argument schemas. REST setup validates configuration; it does not prove credentials by running an action. |
| MCP integrations | Streamable HTTP initialization, tool discovery, negotiated session/version and tool calls | Every call requires approval. No arbitrary stdio server execution, legacy SSE transport or automatic external-app OAuth. |
| Bots talking with each other | Every bot knows its teammates (names, roles, descriptions) and can ask any of them a question or hand off a task with `delegate_task`; the teammate actually runs and its reply comes back. **Teammates › Only selected teammates** in a bot's settings limits it to chosen bots. The receiving chat shows the request as coming from that teammate. While a bot waits, its chat shows what the teammate is actually doing: its step and current action, or that it needs your approval in its own chat | Needs the Bot collaboration tool group (on by default). Cycle prevention, at most two levels and a shared delegation budget, normally four calls. Child task tools retain their own permission checks and approvals. Team rooms with handoffs still limit a turn to the room's selected members. |
| Team rooms | Persistent shared context, exact mentions and bounded coordinator-led collaboration | Context is intentionally shared with selected members. Collaboration is budgeted; it is not an endless bot conversation. |
| Routines | Every N minutes, every day or on chosen weekdays at a time, or once, in an IANA time zone; enable/disable, Run now, per-routine run history, and a choice for runs missed while Tupies was offline (run once when back, or skip). Bots can create the same schedules with approval. | Only the home server schedules, while online; minimum interval five minutes. Clock schedules run at most once per local date, so daylight-saving changes neither skip nor repeat a day; a time inside a spring-forward gap runs an hour later. A busy bot runs its routine when it is free. No cron expressions. |
| Reliable sends | Bot and room messages carry client message IDs. The engine atomically records a receipt with admission; after a lost acknowledgement the browser checks that receipt before retrying. Pending callbacks cannot dispatch across sign-in sessions. | Receipts stay on the admitting engine for a week, at most 200 per bot/room. Room receipts are new in current source. They dedupe Tupies admission, not outside effects; they do not make external actions exactly-once or replay work after restart. |
| Security | Password/bootstrap login, sessions, CSRF/Origin/Host checks, sealed credentials, exact control identities, path checks, safe network transport | Single-owner workspace; no SSO/MFA/RBAC or independent penetration certification. |
| Mac/VPS | Native Node server, container, systemd example, SSH tunnel and optional HTTPS | Operator maintains host patches, TLS and backup encryption. |
| Engines in sync | Home server + linked engines share bots, chats, memory, notes, skills and settings with sealed sync, newest-wins merging and one-engine-per-bot execution. See [sync.md](sync.md). | Hub-and-spoke only; live run progress is not mirrored; model history is last-writer-wins across disconnected engines. |
| Apple app and device pairing | SwiftUI shell for macOS and iOS: QR/link pairing with device keys, target-bound one-hour signed sessions, revocation, engine switching and the engine interface. Installed Mac build 6 includes the official Node runtime and an identity-bound standalone engine; iPhone build 5 retains its existing connections. The explicit migration to `dev.tupies.app` preserved existing device-key access. | Finite existing-install acceptance is recorded in [verification](verification.md). New protocol requires updated engines/apps. Broader device/accessibility QA, public notarized Mac distribution and TestFlight remain separate work. |
| Native iPhone notifications | Sandbox APNs is activated for one retained physical iPhone, with reply/routine categories, opt-in controls, generic private payloads and validated routing. Four owner-observed cases passed: cold tap, manually run routine, matching-chat foreground suppression and Dashboard banner/tap. | These results cover the existing signed installation, not every OS/device/Focus condition. Approval/question alerts and Mac alerts remain separate scope; public distribution is unfinished. See [notification evidence and setup](notifications.md). |
| Device actions | API-oriented engine suitable for future device workers | Computer-use streaming and Mac/iOS action agents are future work. |
| Telegram messaging bots | Token verification, explicit chat AND user allowlists, owned long polling, actual model tasks and bounded plain-text replies | Channels start disabled. Update offsets and reply intents are persisted before side effects; ambiguous deliveries are not retried. Tool approvals remain in Tupies. |
| Other messaging platforms | Not implemented as inbound product interfaces | Discord/Slack inbox adapters need dedicated implementations. The Slack REST integration is an action adapter, not an inbound gateway. |

See [Rich chat and documents](rich-chat.md) for attachment steps, natural-language examples, document specifications and preview limits. Document parsing/rendering runs in stripped-environment workers with Node filesystem read permissions, a 25-second deadline, a 256 MB V8 heap and at most two active workers. These limits reduce exposure; they are not an OS sandbox or security certification.

See [Tool use](tool-use.md) for coding workflows and the comparison evidence. Tupies implements these capabilities in its own engine. Claude Code compatibility is not a runtime dependency or a claim of complete feature parity. Background commands and language servers are scoped to the current task; persistent cross-task services and browser/computer automation are separate work.

Task side effects are never replayed automatically after a restart or ambiguous response. Interrupted tasks retain their transcript and workspace. Files already committed before failure/cancellation remain attached with explicit partial status; a task is not marked completed merely because one file was produced. Inspect the actual result before sending follow-up work. A Stop request cancels Tupies's active operation and child work; external services may already have completed an approved action.

Trusted script/terminal execution runs with the Tupies service account. It is not an OS sandbox and can access what that account can access. Use a dedicated service account/container and restricted mounts. Terminal is off in the default bot tool groups; every script or terminal invocation still requires exact approval.
