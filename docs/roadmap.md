## Exa web search and page reading — 9 November 2026 (source only)

## Mission (1 November 2026, proposed)

The owner requested **Mission** as a separate main tab for goals, verified progress, participants, current work and results. The same Mission can start in that tab or from direct owner chat through explicit intent or conservative recognition of a clear autonomous goal. Promoting an active chat task attaches its existing run and evidence; it must not restart the request or duplicate effects.

The [implementation plan](plans/mission-controller-20261101.md) sequences seven stages: A contract/admission/verifier, B Mission UI and chat entry, C shared resource accounting, D durable waits/Pause/team recovery, E scoped external operations, F isolated general code workers and G measured learning and long-task acceptance. A+B form the first useful release under existing action approvals. Progress derives from verified required outcomes, and run completion alone cannot complete a Mission. Initial execution has one pinned engine; other engines receive presentation-only summaries. This is proposed work, with no Mission implementation or operational rollout included.

## Isolated extension work (1 November 2026)

The extension task has five implementation stages. Source completion and operational installation are separate; no live rollout is implied. See [Tool workshop](tool-workshop.md).

1. **Isolated local tools — implemented in source.** Owner-opt-in synchronous JS/JSON in QuickJS/Wasm, bounded tests and execution, immutable versions, local proposal review/export and initial maintainer/catalog reuse.
2. **Controlled API access — implemented in source.** One exact-approved, assigned REST GET through Engine, bounded JSON passed to a tested transform, credentials kept in Engine, configuration binding and current-access checks. No standing grants or automatic retries.
3. **Bounded autonomous external actions — partially implemented in source.** Owner-issued grants now cover repeated exact REST GETs within one task family: selected bots share a durable request counter and interval, with expiry, revocation, Stop, failure blocking and no restoration of authority after restart. Owner review and grant management are available in chat/Workshop. Monetary budgets, external writes and transactions still need action-specific adapters, outcome checks and uncertain-effect recovery; no guaranteed-profit behavior.
4. **Engine improvement workflow — partially implemented in source.** Separate owner-only source access, exact base hashes, isolated candidate snapshots, fixed syntax checks and bounded QuickJS tests of actual edited pure modules feed the review/export inbox. Maintainers can independently reconstruct/recheck exact edits without applying them. An operator-only pinned-image container verifier now implements fixed syntax/full-suite/web-build steps, isolation preflights, bounded receipts and exact cleanup. A disposable Linux CI workflow exercises full container regressions/build, boundary probes, Stop, stale-base refusal and exact cleanup; see the publication evidence in verification.md. Automatic bot dispatch and controlled release/rollback remain pending. Legacy free-form patches remain unverified; running Engine source is never modified.
5. **Shared contribution delivery — partially implemented.** Local inbox, reviewed export, maintainer re-testing and catalog shipping exist. Hosted opt-in intake, deduplication and reviewed distribution outside product releases remain pending; packages never carry execution grants.

Other runtime/platform acceptance, independent security review and broader real-model usefulness remain cross-stage verification work. Each release still needs its own operational checks and deployment scope.
