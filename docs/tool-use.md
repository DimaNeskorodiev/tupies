# Tupies Engine tool use

Tupies owns its model/tool loop. A bot can discover files, search text, read selected lines, edit exact text, run foreground or managed background commands, query real language servers and update a visible task plan. Tool results feed the next model turn. No Claude Code, Hermes Agent or host Codex installation is needed at runtime.

## Working through a task

For substantial work, the model records a plan with `task_plan_set`. The current plan is persisted with the run, displayed above the work log and included in subsequent model context. Stable step IDs and an optional `expectedVersion` prevent stale plan updates. Only one step can be in progress. Plans describe progress; they do not grant permissions or prove that actions succeeded. If the model ends its answer with unfinished plan steps, the run fails with an explicit incomplete-work notice and preserves the answer and plan. Stop and restart also preserve unfinished steps.

With Workspace enabled, a typical coding workflow is:

1. Call `workspace_glob` with a pattern such as `src/**/*.mjs`, and `workspace_search` with a literal phrase.
2. Read the relevant file with `workspace_read`. Lines and columns start at 1; `nextOffset` and `nextColumn` resume a partial page. The result includes the SHA-256 of the complete file.
3. Call `workspace_edit` with `path`, exact `oldText` and `newText`, and the read result's `sha256` as `expectedSha256`. Ambiguous matches require more context or explicit `replaceAll`. Changed files must be read again. Edits are serialized per file and atomically replaced after another revision check.
4. Read the edited section and, if Terminal is enabled, request `shell_run` for a real verification command. `cwd` selects a private workspace subfolder. `timeoutMs` defaults to 30000 and accepts 100–120000 milliseconds. Every terminal command needs exact approval, including its arguments, folder and timeout. Check `exitCode`, `timedOut` and `truncated` before reporting success.
5. Update the plan to reflect actual verified work, then report the result and any remaining limits.

Balanced policy permits private workspace writes and exact edits automatically. Strict policy requires approval of their exact arguments. Deletes, scripts, commands, integration actions, schedule changes and Manage Tupies changes (creating or changing bots, assigning skills) retain their existing approval requirements. A bot's tool groups, collaborator assignments and active capability snapshots still apply. Reads and edits cannot select another bot's workspace, escape via relative paths or follow symlinks. Approved commands run with the host account's permissions; they are not an OS sandbox.

## Result checks, recovery and evidence

For concrete work, `task_outcome_set` declares up to 12 mechanical checks: a private file exists, contains literal text or matches a SHA-256; an exact command call succeeded; a source was actually read; or a required teammate deliverable completed. Existing criteria cannot be removed or weakened within that run. `task_outcome_check` evaluates them, and the engine checks again before completion. File checks require the active Workspace capability and read the current private bytes; invented or ambiguous tool-call IDs cannot satisfy evidence checks. New `source_read` criteria require an existing successful eligible read: this includes skill contents/inventory, workspace discovery and assigned integration inventory. A list receipt proves that inventory was read, not that its listed integrations work. Search snippets from history or recalled notes remain candidates requiring their original source read. Unsupported, failed or ambiguous observations are rejected before becoming immutable criteria, with an explicit reason. A failed declared check or required teammate result makes the task incomplete. These are model-extracted criteria, not proof that every user requirement was captured or that arbitrary prose is correct. A task with no declared checks is labeled accordingly.

Tool failures include a stable `errorCode`, an action `outcome` and recovery guidance. Invalid inputs, stale state, unavailable capabilities, refusal, transient reads and uncertain actions stay distinct. Explicitly classified transient reads may retry once. Unchanged repeated failures are blocked; a relevant successful file edit can allow another known failed read or command, with ordinary exact command approval still required. Denied or uncertain actions remain blocked from unchanged replay. Normal background-command polling is not a failing-call loop. An MCP `isError` result is retained as a failed integration outcome, never a successful action.

Up to 60 bounded work receipts per task record tool identity, observed status, time, source/file version and output references, without full payloads. They remain in the last 50 local run records and never sync. `work_records_read` pages these observations and lists recent visible run IDs; the same third-party conversation exclusions as history retrieval apply. Receipts are redacted on write and read. **Recent tasks → Checks and tool activity** presents the actual checks/observations on demand. Plans, memories and receipts never grant permissions.

`delegate_task` accepts optional `expectedOutput` for a required mechanically checked deliverable. Omit it for a question or a status self-report; a received reply alone does not certify a healthy integration. It returns the real child's status, output, checks, unmet requirements and scoped artifact references. A completed child without passing declared checks is partial when an expected output was required. The parent cannot complete while such a required result is incomplete. Repair uses the original teammate and engine-owned `deliverableId`; attempts and original criteria remain immutable. Failed source-check repairs retain the original check ID and exact bounded read request when its recorded digest matches. Successful historical reads need not be replayed. Missing identities and uncertain actions remain explicit blockers. Child artifact paths do not grant access to another bot's private workspace. Existing depth, cycle, shared-call budget and cancellation limits remain.

For independent checks across a team, enqueue every request with `delegate_task {botId,task,wait:false}` before collecting results. The immediate engine-owned `delegationId` acknowledges the queue entry, not child success. `delegation_status` lists current-parent jobs and their actual results; optional waiting is bounded and never starts a second copy. Valid status polls with genuinely pending children count as waiting, so an unchanged long-running child is not cancelled by the repeated-work detector. Invalid or repeatedly unchanged terminal polls retain ordinary no-progress checks. The engine runs queued jobs as concurrency slots become available, so a large team need not run sequentially or exceed resource limits. Exact IDs cannot select another parent's jobs. Parent completion requires outstanding work to settle and its results to be collected. Stop cancels queued work and active children; restart does not replay queued or uncertain work. The legacy default waits for one child and remains appropriate for a genuinely dependent handoff. `teammate_completed` can refer to an exact `delegationId`; a queued acknowledgement cannot satisfy it.

Active wait dependencies are also checked for cycles. If two coordinators are waiting back on one another, one undispatched queue entry returns `concurrency_blocked` with `reason:"dependency_cycle"`, even when global slots remain. An unrelated busy teammate without a dependency back remains queued normally. Exhausted slots held entirely by waiting coordinators also produce an explicit undispatched refusal instead of a permanent wait. Neither case authorizes cancelling another owner's task or replaying an uncertain action.

With Workspace and model image input, `workspace_image {path}` shows a PNG, JPEG or WebP through the existing bounded document worker and provider image-parts route. It is not offered to text-only models. The newest-five image limit, private paths, cancellation and active capability snapshot still apply.

With Web enabled, `web_search {query,count?}` uses keyless DuckDuckGo discovery through Tupies's public HTTPS transport. Queries go to DuckDuckGo; no Python/CLI installation is needed. Results are bounded public URL/title/snippet candidates, not fetched-page evidence. Use `http_fetch` or the read-only browser to verify a source. Challenge, rate-limit, timeout or changed-layout failures are explicit and do not mean no results. No other provider is selected automatically. The owner may select an assigned [SearXNG fallback](searxng.md) in Bot Advanced settings. Only a real DDG failure requests one exact-approved fallback call; a genuine empty result never does. Its provider and primary failure remain visible. Explicit assigned SearXNG, Tavily and Brave integrations also remain available through `integrationId`, with Web + Integrations and exact approval of integration/query/count; changed credentials/configuration invalidate that request. No unrelated service is chosen from discovered credentials. See [evaluation](evaluation.md) for deterministic and explicit real-model checks.

## Managed background commands

Approved commands, skill scripts and language servers use an engine-local per-bot `process-homes/<botId>/` for HOME, XDG configuration/cache/data and temporary files. Their working folder remains the explicitly approved private workspace/project (or assigned skill folder). Model workspace writes cannot place startup configuration in this home. Python user-site loading and system Git configuration are disabled; Git's global configuration is confined to the process home. Environment overrides also disable automatic Git filesystem-monitor commands, repository hooks, credential helpers and the external-command transport. Changing `.git` metadata, `.gitconfig` or `.gitattributes` through workspace writes/edits/exports always requires exact approval, including Balanced. This prevents an unreviewed configuration edit from hiding code execution behind a normal Git command. Explicit command-line overrides and arbitrary approved builds/project code still have host-account permissions: this is not an OS sandbox. Provider/host environment credentials are not inherited. Existing workspace dotfiles are preserved but never copied into trusted configuration automatically. Back up the process-home tree, keep credentials there protected, and configure tools independently on each engine; it does not sync.

With Terminal enabled, `shell_start` requests exact approval of `{executable,args,cwd?,timeoutMs?}` and returns an opaque process ID after the command starts. The engine can continue file work or start another approved command while it runs. `shell_list` lists this task's commands. `shell_read` accepts `{processId,offset?,limit?,waitMs?,outputVersion?}` for merged, redacted stdout/stderr and real status; offsets count UTF-16 characters and a read can wait up to 10000 ms for new output or exit. Carry the returned `outputVersion` (including version 0) on later nonzero pages. If new credential redaction changes an already visible prefix, a stale cursor returns 409 and must restart at offset 0; the browser clears mismatched pages and offers Refresh. Only `status:completed` with `exitCode:0` demonstrates command success. New output may arrive before exit, so read again at the retained length to wait for completion. `shell_stop` stops only an owned handle and waits for cleanup; it cannot select an arbitrary PID.

The chat shows command status, folder, bounded arguments/output previews and exit details. View output opens a paged read/refresh dialog. Stop command leaves the bot and its other work running. Both UI APIs require authentication and current bot/run/process identities; stopping also requires CSRF and the current remote run identity. Late responses cannot replace another task's output dialog or make a stopped command look running again.

Commands belong to their task. They stop and drain on Stop, failure, runtime limits, successful task end or shutdown. A final model answer while a background command is still running fails explicitly and preserves the available work. The model must wait for the command or intentionally stop it before finishing. These are concurrent task-owned sessions, not persistent service hosting across completed tasks.

There are at most four active commands per task, eight globally and 20 command histories per task. Command timeout defaults to five minutes and accepts 100–1800000 ms, while the task's own deadline still applies. Output stops at 250000 raw bytes; overflow terminates the command with explicit output-limit status. Split UTF-8 characters and known credentials split across chunks are handled before output is exposed. Credential rotation refreshes the old/new secret union, and complete retained text is redacted before pagination/persistence; unrelated short readiness messages remain visible immediately. At most 12000 redacted characters per command are persisted as a preview; full bounded output stays in process-manager memory until task cleanup. Later/restarted reads identify prefix-only coverage explicitly.

Each command uses a Tupies-owned guardian. Loss of the host IPC connection terminates the ordinary process group, including descendants that ignore TERM. Restart marks unfinished metadata interrupted and never relaunches a stored command or adopts/signals a historical PID. On Windows a process-tree termination route exists; execution verification was performed on macOS. A command deliberately escaping its process group still falls within the documented trusted-host execution boundary.

## Language-server intelligence

`lsp_start` requests exact approval of `{server:"typescript",rootPath?}` or `{server:"custom",executable,args,rootPath?}`. Both Workspace and Terminal must be enabled to launch it. The bundled TypeScript/JavaScript preset uses pinned runtime dependencies `typescript-language-server` 5.3.0 and TypeScript 6.0.3, supporting the project's Node 22.16+ baseline. It selects the shipped compiler, disables automatic type acquisition and does not enable project-local plugin loading. Custom servers must already be installed; the tool does not install packages. All language servers are trusted host processes with host-account permissions, not isolated filesystem sandboxes. Selecting a project root constrains tool file selection and returned locations; it does not sandbox the approved server's own imports or filesystem access.

The server returns a session ID and explicit supported capabilities. `lsp_query` uses the following operations when the server advertises them:

| Operation | Inputs and result |
| --- | --- |
| definition, type_definition, implementation | `path`, `line`, `character`; normalized private project locations. |
| references | Same position inputs; optional `includeDeclaration` defaults true. |
| hover | Same position inputs; bounded text and optional source range. |
| document_symbols | `path`; named symbols with kinds and private locations. |
| workspace_symbols | `query`; named symbols across the selected project. |
| prepare_call_hierarchy | Source position; bounded items with opaque session-owned `itemId` values. |
| incoming_calls, outgoing_calls | An `itemId` returned by the same session; normalized call items and call-site ranges. Changed source invalidates the prepared item; prepare again. |
| diagnostics | `path`; actual server reports plus received/version/freshness/truncation fields. |

Source positions are 1-based UTF-16 code units. Tupies uses standard Content-Length JSON-RPC, initializes the server, synchronizes opened documents and changed content before querying, and closes vanished open files. Outside-project file URIs, symlinks and malformed locations are omitted with explicit coverage metadata. Opaque hierarchy data stays internal and never becomes a model-authored server command. The client refuses `workspace/applyEdit`, arbitrary command execution and unsupported server-initiated requests; edits continue through Tupies's normal file tools and approvals.

Diagnostics use pull reports when supported, otherwise bounded push notifications. No report within the two-second wait returns `received:false`, not an empty-success assertion. Unversioned push reports are labeled `versioned:false`; they cannot prove an exact source revision even after document synchronization. Server text is untrusted evidence. Missing capabilities and protocol failures produce tool errors, and all server processes drain at task end.

There are at most two language servers per task, four globally and 20 opened files per session, each up to 1 MB. Responses cap locations/symbols/diagnostics at 100 items; call hierarchy caps 30 items, 20 call-site ranges per item and 100 retained hierarchy handles. Additional text/frame/output limits report truncation or failure explicitly: 2 MB per protocol frame and 16 MB protocol output per session. See [API](api.md) for exact tool schemas and [verification](verification.md) for real bundled-server and crash-cleanup evidence.

The protocol follows Microsoft's [LSP 3.17 specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/). The preset uses the maintained [TypeScript Language Server](https://github.com/typescript-language-server/typescript-language-server), rather than an approximate text-search implementation.

## Batches and long results

Up to four adjacent, explicitly classified read calls can run together. Every mutation, approval, delegation or unknown tool is an ordering barrier for that tool batch. Asynchronous delegation has its own queue: `wait:false` returns after admission so later handoffs can be enqueued while children work. Results enter provider history in original call order. A failed read returns an error result while successful siblings remain usable. Stop aborts all started reads and drains the batch before history is reconciled. Commands and integration calls are never parallelized by this mechanism.

Results larger than 16000 characters return a short preview and a `resultId`. Use `tool_result_read` with that ID and follow `nextOffset`. Outputs are redacted before retention. Up to 250000 characters per result and 1000000 characters per active run are retained in memory; the oldest retained results expire first. Results expire when execution ends, and full retained text is excluded from run polling and persistent state. Read pages are at most 12000 characters and shrink further when JSON escaping needs space. `truncated` distinguishes a retained prefix from the complete source result. Missing or expired results require a new, narrower read.

All calls, including plan updates and result pages, count toward the existing 60-call task budget. Model-step and wall-clock limits remain enforced. Workspace reads are targeted, not a promise to ingest an entire 1 MB file in a single task. Search scans at most 4000 entries, 20 directory levels, 1 MB per file and 8 MB total per call. Binary/skipped reads count toward the byte budget. Globs support `*`, `**` and `?`; content search is literal. Discovery skips `.git`, `.tmp` and `node_modules`, plus other hidden paths unless explicitly requested. Scan truncation and skipped counts are returned; no matches do not establish absence outside that boundary.

Tupies retains its own bots-first architecture, private workspaces and security policy. Background commands and real LSP navigation/diagnostics are implemented as described above. Signed-in or form-filling browser work, computer actions, arbitrary host project mounts, git worktree management and file-rewind checkpoints remain future work. Interactive questions (`ask_user`) and attached-image understanding are covered in `docs/capabilities.md`. Full Claude Code parity is not claimed from this delivered toolset. Assigned REST/MCP integrations, bounded real bot delegation, skills, memory and document output provide extension paths within their documented permissions.

A new subtopic can call `memory_refresh {query}` without rewriting the plan. It shares the maximum three recall passes with admission/plan/compaction refreshes and keeps the system prefix stable. Recent task evidence includes bounded context/memory/summary coverage; Memory facts have a collapsed Source and changes disclosure. Source-read checks require successful HTTP responses when status is available, and teammate `sources` are derived only from successful recorded reads, never model-invented references.
